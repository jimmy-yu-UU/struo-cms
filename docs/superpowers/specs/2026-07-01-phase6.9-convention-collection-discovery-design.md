# Phase 6.9 — Convention-based Collection Discovery (Design)

> **Status:** design (approved in brainstorm 2026-07-01)
> **Type:** framework/host decoupling refactor — the prerequisite the roadmap gates Phase 7 on
> ([`docs/ROADMAP.md`](../../ROADMAP.md) §"Open architectural decisions" → "Framework vs. host").
> **Risk:** low. Startup-wiring only; no change to query, permission, persistence, or auth paths.

## 1. Motivation

StruoCMS is intended to be a **reusable CMS base template**. The target workflow is: start from
this repo, add project-specific `[CmsCollection]` classes, and get CRUD APIs automatically — with no
edits to framework bootstrap code.

Today `Struo.Api` names a specific content model at compile time, which blocks that workflow:

- `Program.cs:36` — `AddStruoMetadata(typeof(Article).Assembly)` uses `Article` as the anchor for
  *which assembly to scan*.
- `Program.cs:115–121` — the development `InitTables` call passes a **hand-maintained** list of
  entity types (`Article`, `ArticleTranslation`, `Category`, plus framework built-ins).
- `Program.cs:14` — `using Struo.Sample.Blog;`.

Consequence: adding a collection today requires editing `Program.cs` (register its assembly, add it
to the `InitTables` list). That is exactly the coupling this phase removes.

**Important:** the scanner itself is already content-agnostic. `MetadataScanner.Scan`
([`MetadataScanner.cs:25`](../../../src/Struo.Infrastructure/Metadata/MetadataScanner.cs)) already
reflects over **all** `[CmsCollection]` types in whatever assemblies it is given. The only hard-coded
things are (a) *which assembly* and (b) the *InitTables type list*. This phase replaces both with
convention/config; it does not touch scanning, query, or persistence logic.

## 2. Goals / Non-goals

**Goals**
- `Program.cs` names **no** content type. Adding a collection never requires editing it.
- Support two development styles equally, per the confirmed product model:
  1. **Develop directly in the template** — add `[CmsCollection]` classes straight into the host
     (`Struo.Api`) or the existing content project. **Zero configuration required.**
  2. **Separate content project** — keep collections in their own assembly; name it in config.
- Ship a **clear developer document** explaining how to add a collection (explicit deliverable).

**Non-goals (YAGNI)**
- No runtime/dynamic collection definition (no DB-stored schema, no admin "collection designer").
  Collections remain code-defined C# classes discovered at startup — this is Model 1, confirmed.
- No plugin system, no NuGet packaging of the framework. This stays a single-host template.
- No change to production schema management (still reviewed migrations; `InitTables` stays
  Development-only, guarded by `DatabaseInitializer`).

## 3. Design

### 3.1 Assembly discovery convention

Metadata is scanned from the union of three sources:

1. **Framework assembly** — always (built-ins: `Language`, `File`, `FileTranslation`, `User`,
   `Role`, `Permission`, `UserRole`). Already done today via
   `typeof(MetadataServiceCollectionExtensions).Assembly`.
2. **Host assembly** — always. `Program.cs` passes its own assembly explicitly
   (`typeof(Program).Assembly`, i.e. `Struo.Api`). *This is what makes "develop directly in the
   template" need zero configuration:* a `[CmsCollection]` class dropped into `Struo.Api` is found
   automatically. Passing it explicitly (rather than `Assembly.GetEntryAssembly()`) is deterministic
   under `WebApplicationFactory<Program>`, where the entry assembly is the test runner, not the API.
3. **Configured content assemblies** — optional. Assembly names listed under
   `Struo:ContentAssemblies` are loaded via `Assembly.Load(name)` and scanned. Only needed when
   content lives in a separate project (e.g. `Struo.Sample.Blog`).

Assemblies are de-duplicated before scanning (an assembly may satisfy more than one rule).

### 3.2 API surface change: `AddStruoMetadata`

Add a configuration-driven overload; keep the existing explicit-assembly overload for tests.

```csharp
// New — used by Program.cs. Applies the §3.1 convention.
public static IServiceCollection AddStruoMetadata(this IServiceCollection services, IConfiguration config);

// Existing — retained. Tests pass explicit assemblies; framework assembly still auto-appended.
public static IServiceCollection AddStruoMetadata(this IServiceCollection services, params Assembly[] assemblies);
```

The config overload resolves the assembly set per §3.1, then delegates to the existing scanning code
path unchanged (same `CachedMetadataProvider`, `EntityRegistry`, `RelationshipGraph` registrations).

Behavior on a bad `Struo:ContentAssemblies` entry (assembly name cannot be loaded): fail fast at
startup with a clear message naming the offending entry — never silently skip (matches the
fail-fast metadata philosophy already in `MetadataScanner`).

### 3.3 Automatic InitTables entity collection

Replace the hand-maintained `typeof(...)` list with a collector that returns every type needing a
table. It composes **already-scanned** metadata (so it stays consistent with what the API exposes):

- **Content collection types** — from `IEntityRegistry` (the `[CmsCollection]` types).
- **Translation sidecars** — from each collection's `TranslationMetadata.TranslationEntityType`
  (via `IMetadataProvider`).
- **M2M junction types** — from the relationship graph's mapping types
  (`IM2MDescriptorSource` / `RelationshipGraph`).
- **Framework built-in entities** — a fixed list owned by Infrastructure
  (`Language`, `File`, `FileTranslation`, `User`, `Role`, `Permission`, `UserRole`). Some are also
  `[CmsCollection]` and thus already in the set; the union is **de-duplicated**.

Exposed as a small collector (e.g. `IEntityTypeCollector.CollectForInitTables()` or a method on the
registry) registered in DI. `Program.cs` calls
`DatabaseInitializer.InitializeDevelopmentSchema(db, env, collector.CollectForInitTables())` — no
content type named.

### 3.4 `Program.cs` after the change

- Remove `using Struo.Sample.Blog;` (line 14).
- `AddStruoMetadata(builder.Configuration, typeof(Program).Assembly)` (was `typeof(Article).Assembly`).
  The host assembly is passed explicitly (rule 2); config supplies any extra content assemblies.
- `InitTables` fed by the collector (was the explicit `typeof(...)` list).
- The seeders (`LanguageSeeder`, `AdminUserSeeder`, `RbacSeeder`) are unchanged — they already take
  config values, not content types.

Net: `Program.cs` becomes fully content-agnostic.

### 3.5 Isolation / boundaries

- The collector and the config-overload live in `Struo.Infrastructure.DependencyInjection`
  (already the home of `AddStruoMetadata`). No new cross-layer dependency; `Api` still depends only
  on `Infrastructure` + `Application`.
- The framework built-in entity list is owned by Infrastructure (it already owns those types),
  keeping the "framework knows its own tables" responsibility in one place.

## 4. Developer documentation (explicit deliverable)

A new guide page — `docs/guide/03-adding-a-collection.md` — written to be understandable by a
developer new to the codebase. It must cover, with a complete copy-pasteable example:

1. What a Collection is (a `[CmsCollection]` C# class) and where to put it (in `Struo.Api` for the
   direct-template style, or in a content project named in `Struo:ContentAssemblies`).
2. The `[CmsField]`, `[CmsOptions]`, `[CmsRelation]`, `[CmsTranslations]` attributes — what each
   does, shown on one worked example (fields + a select + a relation + a translation sidecar).
3. The discovery convention (§3.1) stated plainly: "add the class, restart — it is scanned, its
   table is created in Development, and it appears at `/api/schema` and `/api/items/{collection}`."
4. What is auto-created vs. what needs config (the zero-config host case vs. the separate-project
   case).
5. The Development-only `InitTables` behavior and the production migration note (link to
   getting-started).

`docs/ROADMAP.md` is updated: mark the "Framework vs. host" open decision resolved (convention-based
discovery, template model), and add a Phase 6.9 row.

## 5. Testing (TDD)

Unit (SQLite / pure), written failing first:

- **Entity collector** — given a set of scanned collections with a sidecar, an M2M junction, and the
  framework built-ins, returns the exact expected type set, **de-duplicated**, order-insensitive.
- **Collector composition** — a content collection with `[CmsTranslations]` contributes its sidecar;
  an M2M relation contributes its junction; a plain collection contributes only itself.
- **Config discovery** — `Struo:ContentAssemblies` empty ⇒ only framework + entry assembly scanned;
  a listed, loadable assembly ⇒ its collections appear; an unloadable name ⇒ fail-fast with a
  message naming the entry.
- **Host-assembly convention** — a `[CmsCollection]` type in the entry assembly is discovered with
  no config (simulated by passing the test assembly as the entry-equivalent).

Integration (existing harness):

- App boots; `GET /api/schema` still returns `article` (and its translated fields); `GET
  /api/items/article` still works — i.e. behavior is identical to before the refactor.
- The full existing suite (246 tests) stays green — it is the primary safety net.

## 6. Verification gate (acceptance)

Done when **all** hold, with evidence:

1. `dotnet build` clean (warnings-as-errors).
2. `dotnet test` — new tests pass; previous count (246) does not regress.
3. `Program.cs` contains no content-type name and no `using Struo.Sample.Blog` (grep evidence).
4. App boots against live PostgreSQL; `InitTables` creates the same tables as before (spot-check
   `article`, `article_translation`, `category`, plus built-ins); `/api/schema` and
   `/api/items/article` return as before.
5. **Manual smoke of the core promise:** add a throwaway `[CmsCollection]` class directly in
   `Struo.Api`, restart, confirm its table is created and it appears at `/api/schema` **without any
   edit to `Program.cs` or config**. Then remove it.
6. `docs/guide/03-adding-a-collection.md` exists, follows the example end-to-end, and a reader can
   add a collection from it alone. `ROADMAP.md` updated.

## 7. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Missing an entity in the auto-collected list ⇒ a table not created | Collector composes the *same* scanned metadata the API uses; integration test asserts the known tables; live boot spot-check in the gate. |
| Entry assembly ambiguous under `WebApplicationFactory<Program>` (it is the test runner, not the API) | Host assembly is passed explicitly as `typeof(Program).Assembly`, not derived from `Assembly.GetEntryAssembly()`. The integration factory also lists `Struo.Sample.Blog` in `Struo:ContentAssemblies`, so sample content loads regardless. |
| A configured content assembly's DLL isn't in the output folder | Fail-fast with a clear message; documented in the guide (a separate content project must be referenced so its DLL ships, or listed correctly). |
| Duplicate collection names across host + content assembly | Already handled — `MetadataScanner.ScanTypes` throws on duplicate collection name. |
