# StruoCMS — Phase 5.6 (Multilingual SEO) Design

> Date: 2026-06-29
> Source of truth: the StruoCMS master spec (§0–§18) + Phase 0–5.5 specs.
> Depends on Phase 5.5 (merged): entity `Guid` PKs and `Guid` translation FKs.
> Each phase runs its own brainstorm → write-plan (TDD) → execute-plan → verify cycle (§17.1).

## 1. Goal & scope

Make SEO fields per-locale by moving them onto the translation sidecar, and resolve a per-locale
OG image into its `File` object on read. Establish **one** way to declare SEO: the translation
sidecar.

**In scope:**
- New Domain `SeoTranslation` abstract base carrying translatable SEO fields (`SeoTitle`,
  `SeoMetaDescription`, `SeoOgImageId`).
- `ArticleTranslation : SeoTranslation`; the sample `Article` drops its parent SEO fields/relation.
- **Retire `ISeoMeta`** (the parent-side SEO convention) entirely.
- Extend the translation overlay to resolve `Image`-typed translatable fields into the referenced
  `File` (per locale), eagerly, via the existing batch-load path.
- TDD coverage + live-Postgres verification gate.

**Out of scope (deferred / unchanged):**
- `OnDelete` enforcement for `SetNull`/`Cascade` (parent OR sidecar) — the framework enforces only
  `Restrict` today; per-locale image deletion behavior is deferred to a future "OnDelete enforcement"
  phase that covers parent and sidecar references uniformly.
- A general relation-graph-over-sidecars (full `[Navigate]` on translation entities) — not needed;
  the overlay resolution is the targeted mechanism.
- Admin SPA rendering of per-locale SEO editors (Phase 7).
- Auth/RBAC (Phase 6).

## 2. Key decision: SEO is sidecar-only (single path)

SEO fields may be declared **only** on the translation sidecar (via `SeoTranslation`). `ISeoMeta`
(parent-side SEO) is removed.

**Rationale:** Two ways to introduce SEO (parent interface + sidecar base) means two mental models
to maintain. This is an i18n-first CMS where SEO-bearing content (articles, pages, products) is
almost always content that should be translatable, so "has SEO ⊆ has translation sidecar" fits real
usage. One mechanism is simpler to maintain and document.

**Accepted tradeoff:** A collection that genuinely needs SEO but never needs multiple languages must
still declare a translation sidecar (holding at least the SEO fields) and go through the
default-locale translation flow. This is mild: the i18n machinery already supports "default locale
only" gracefully, and in a single-language deployment the admin UI shows just one language's SEO
fields. If a real "non-i18n collection with SEO" need arises later, revisit adding a parent path then.

**Why not a parent base class:** C# single inheritance — entity parents already inherit
`AuditableEntity` (Phase 5.5), so they cannot also inherit a `SeoFields` base. A parent SEO path
would have to be an interface convention (`ISeoMeta`) or per-field declaration, which is exactly the
second mechanism we are removing. Translation sidecars are plain POCOs with no base, so a
`SeoTranslation` base works cleanly there.

## 3. Backend already bounds editable locales to enabled languages

Per-locale writes/reads are validated against the `language` collection's enabled entries:
`ItemService` calls `languages.IsEnabled(locale)` on create/update/query and rejects unknown/disabled
locales (`QueryException` → 400). So per-locale SEO editing is already bounded to enabled languages;
the Phase 7 admin UI will render one editor per enabled language. No backend change needed for this.

## 4. Components

### `SeoTranslation` (new — `src/Struo.Domain/Seo/SeoTranslation.cs`)
Domain, zero external packages, but carries `[CmsField]` (a Domain attribute — allowed by §2, unlike
`[SugarColumn]`):

```csharp
using Struo.Domain.Metadata.Attributes;
using Struo.Domain.Metadata.Enums;

namespace Struo.Domain.Seo;

/// <summary>
/// Base for translation sidecars that carry SEO. SEO is declared ONLY on the sidecar (per-locale);
/// the parent-side ISeoMeta convention is retired (see Phase 5.6 design §2). Subclasses are
/// translation entities (POCO, no other base), so this base class is usable there.
/// </summary>
public abstract class SeoTranslation
{
    [CmsField(Label = "SEO Title", Interface = FieldInterface.Text, Group = "SEO", Sort = 10)]
    public string? SeoTitle { get; set; }

    [CmsField(Label = "SEO Description", Interface = FieldInterface.Textarea, Group = "SEO", Sort = 11)]
    public string? SeoMetaDescription { get; set; }

    [CmsField(Label = "OG Image", Interface = FieldInterface.Image, Group = "SEO", Sort = 12)]
    public Guid? SeoOgImageId { get; set; }
}
```

`ArticleTranslation : SeoTranslation` — the scanner's `ScanTranslations` enumerates inherited
`[CmsField]` properties (`GetProperties(Public|Instance)` includes inherited) and marks them
`Translatable = true`, so the three SEO fields become translatable, SEO-grouped fields automatically.

### `Article` / `ArticleTranslation` (sample)
- `Article`: stop implementing `ISeoMeta`; remove `SeoTitle`/`SeoMetaDescription`/`SeoOgImageId`
  columns and the parent `SeoOgImage` `[Navigate]`/`[CmsRelation]`. Keep `[CmsFieldGroup("SEO")]` so
  the group exists. (`Article` keeps inheriting `AuditableEntity`.)
- `ArticleTranslation : SeoTranslation` — inherits the three SEO fields; keeps its own `Id`
  (`long IsIdentity`), `ArticleId` (`Guid`, from 5.5), `Locale`, `Title`, `Body`.

### Scanner / metadata (`MetadataScanner`)
- **Remove** the `ISeoMeta` block (`MetadataScanner.cs:95-102`) and `BuildSeoFields()`.
- No new scanner logic for SEO — translatable fields (incl. the inherited SEO ones) already flow
  through `ScanTranslations`.

### Delete `ISeoMeta` (`src/Struo.Domain/Seo/ISeoMeta.cs`)
Only `Article` implements it; removed there. No other consumers.

## 5. Data flow — per-locale image resolution (the one new capability)

`ItemService.OverlayTranslationsAsync` gains a resolution step. After grouping translation rows into
the per-locale field maps:

1. From the collection metadata, find translatable fields whose `Interface == FieldInterface.Image`
   (convention: `Image`/`File`/`Files` fields reference the `file` collection).
2. Collect the distinct non-null `Guid` values of those fields across all locales/rows.
3. Batch-load via the existing `repository.QueryWhereInAsync("file", "id", ids)` (no new repo method).
4. Project each `File` with the existing `Project`/`ProjectFor` (permissions + readable-fields apply).
5. For each locale field map, inject a resolved object beside the raw id: `seoOgImage` (the projected
   `File`, or `null` if the id is null/dangling) alongside `seoOgImageId`.

Result per locale:
```jsonc
"translations": { "en": {
  "title": "...", "body": "...",
  "seoTitle": "...", "seoMetaDescription": "...",
  "seoOgImageId": "07c2...",
  "seoOgImage": { "id": "07c2...", "fileName": "og.png", "contentType": "image/png",
                  "width": 1200, "height": 630, "status": "published" }
}}
```

**Eager** (always resolved): it is one extra batched query, SEO rendering needs the URL/dimensions,
and it mirrors how the `translations` overlay itself is always applied. Naming: the resolved key is
the field name with the `Id` suffix stripped (`seoOgImageId` → `seoOgImage`), mirroring the parent
`categoryId`/`category` convention.

## 6. Error handling / edge cases

- A `seoOgImageId` that is null or points at a missing/deleted `File` → `seoOgImage: null` (no throw;
  consistent with no `SetNull` enforcement — a dangling reference is possible and handled gracefully).
- A locale with no SEO values → the SEO keys are simply absent/null for that locale; `seoOgImage` null.
- Empty article set / no translation sidecar → overlay is a no-op (unchanged).
- Permissions: if the `file` collection is not readable, the projected `File` honors
  readable-fields/permission rules already enforced by `Project`.

## 7. Testing (TDD — RED first)

Unit / integration (SQLite in-memory):
1. **Scanner:** `ArticleTranslation` exposes `seoTitle`/`seoMetaDescription`/`seoOgImageId` as
   `Translatable = true` in the `SEO` group; `Article` no longer exposes parent SEO fields; the
   `article` schema's field list contains no parent `seoTitle`/`seoOgImageId`.
2. **`ISeoMeta` removed:** no type `ISeoMeta` remains; `Article` does not implement it; the scanner has
   no parent SEO block (compile + a metadata test that a non-translation collection gets no auto SEO).
3. **Per-locale SEO round-trip:** create an article with distinct SEO per `en`/`zh` (title, description,
   image id); read back → each locale shows its own SEO values.
4. **Image resolution:** create a `File`; set its id as `en`'s `seoOgImageId` only → `en.seoOgImage` is
   the nested projected `File`, `zh.seoOgImage` is `null`. Dangling id (random Guid) → `null`.
5. **Eager batch:** two articles each referencing the same file across locales resolve correctly
   (one IN load, no N+1).

Live Postgres verification gate (memory: *SQLite green ≠ Postgres correct*):
6. On real PG: `article_translations` has `seotitle`/`seometadescription`/`seoogimageid` columns
   (text/text/uuid; uuid nullable); `articles` no longer has the three SEO columns.
7. Per-locale SEO + image-resolution round-trip works on PG (no bigint/uuid cast error; `seoOgImage`
   resolves the `File`).

## 8. Migration

Dev-only `InitTables`; **drop & recreate** `articles` (loses `seotitle`/`seometadescription`/
`seoogimageid`) and `article_translations` (gains them). No data migration. Existing dev DBs recreate.

## 9. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Inherited `[CmsField]` on `SeoTranslation` not picked up by `ScanTranslations` | Scanner uses `GetProperties(Public\|Instance)` (includes inherited) + `[CmsField]` filter; covered by test 1. (Same inheritance-scan path Phase 5.5 relied on.) |
| Image field → `file` collection is a convention, not explicit | Documented; `Image`/`File`/`Files` interfaces map to `file`. If a future field needs a different target, revisit (YAGNI now). |
| Eager resolution cost on large lists | Single batched `IN` load across all locales/rows; acceptable. |
| Dangling image id after a `File` delete | Resolves to `null` (no enforcement; deferred OnDelete phase). |
