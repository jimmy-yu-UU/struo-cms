# 9. 版本紀錄與軟刪除

每一次寫入怎麼留下可以回頭看的快照、刪除又怎麼變成一件可以挽回的事，是這一章的主題。

## 逐集合啟用版本紀錄

版本紀錄用 `[CmsCollection]` 的 `Revisions = true` 開啟，與軟刪除各自獨立，兩個都不開、只開一個或都
開都可以；選項本身見[第 5 章：定義集合](05-collections.md)。每筆版本紀錄都存在同一張共用資料表裡，用
集合名稱、項目 id 與版本編號當鍵；框架自己的集合都沒有開，範例的 `Article` 開了，同時也實作
`ISoftDeletable`，是唯一同時具備兩者的集合。

開啟之後不需要再呼叫任何端點：建立、更新、還原到某一筆版本、丟進垃圾桶與從垃圾桶復原，都
會在原本那筆寫入的同一筆交易裡順便留下一筆版本紀錄，寫入路徑本身就是唯一的入口。

## 快照包含什麼、何時擷取

快照是在那一列資料真正寫進資料庫之後，直接從已落地的實體建出來的，而且刻意完整保留原樣：
不套用欄位層級的 RBAC 過濾，也不跳過標成隱藏的欄位，因為日後的還原必須能把整個項目狀態復
原回去，不管誰之後會讀到這筆紀錄。

快照是一個攤平的 JSON 物件，內容固定：

- `id`。
- `version`——只有實體繼承 `AuditableEntity` 時才有。
- 每一個自己宣告的 `[CmsField]`，系統管理欄位與可翻譯欄位除外；`Json` 介面的欄位會把原始
  文字解析回真正的 JSON 值，而不是存成一個字串。
- 每個多對一關聯的外鍵 id，鍵是關聯的 camelCase 名稱。
- 每個多對多關聯，鍵是關聯名稱。
- `translations`，裡面是這個項目存在資料列的每一個 locale，是完整的翻譯狀態，不只是目前查詢
  用的那個 locale。

多對多關聯裡，junction 不帶 payload 的關聯存成一個有序的 id 陣列；junction 帶 payload 的
關聯存成一個有序的 `{ id, ...payload }` 物件陣列，每個已連結目標各一筆，連隱藏的 payload
欄位值都會收進去。有宣告排序欄位時，順序依那個欄位排。

快照的形狀刻意跟一份更新請求的 body 一致，還原才能直接走一般的更新路徑，不需要另外一套復
原邏輯。單純 id 陣列的快照還原時只當成成員異動，junction 上已經存在的 payload 值不會被動
到。

建立、更新、還原、丟進垃圾桶與復原都會寫下一筆版本紀錄，而且每一次擷取都在跟那次寫入相同
的資料庫交易裡完成，寫入回滾時不會留下孤兒紀錄。

還原留下的那筆紀錄額外帶著被重新套用的版本編號，其餘四種操作這一欄一律是空的。

丟進垃圾桶與復原這兩種擷取還多一個條件：只有那次的軟刪除更新真的影響到某一列時才會記，所
以兩個呼叫同時搶著丟同一列不會各記一筆重複紀錄，重複丟一個已經在垃圾桶裡的項目也不會留下
任何紀錄。

擷取失敗會讓整個丟進垃圾桶或復原一起回滾，不會出現半丟進垃圾桶、卻沒有對應紀錄的狀態。

一次什麼都沒改的更新，一樣會寫下一筆更新紀錄——寫入路徑永遠會真正送出這次更新、永遠會把
版本號往前推，並不會比較新舊值，這一點在估算這張表會有多大時要記得。版本編號是同一個集
合、同一個項目底下目前最大編號加一，從 1 開始，連同目前的時間與操作者一起記下。

存版本紀錄的這張表是框架自己的表，不是一個 `[CmsCollection]`，因此完全不能透過通用的項目
API 瀏覽。它只會被寫入，不會被更新，也不實作稽核介面（沒有更新時間與更新者）。

表上有一組涵蓋集合名稱、項目 id 與版本編號的複合唯一索引，是防止併發搶號的最後一道防線，
開發環境啟動時還會另外檢查一次；這個索引只在資料表本身還不存在時由建表流程一併建出來，不
會回頭補到已經存在的表上。例外跟翻譯 sidecar 的索引一樣：開了 `Database:AutoSyncSchema`
的 Development 環境會在完整同步時試著補上。

版本紀錄會一直留著：列表端點回傳這個項目的全部紀錄，不分頁，也沒有保留期限或清理排程；唯
一會清掉版本紀錄的動作是永久刪除（`?purge`，本章稱為清除）。一個寫入頻繁又開了版本紀錄的
集合，這張共用表會無上限地成長。

### 隱藏欄位在快照中的遮蔽

因為快照會把整個項目連同隱藏欄位一起收進去，交給外部呼叫端的那份就一定不能洩漏任何一個隱
藏值。對外讀取時會拿到一份遮蔽過的副本，拿掉：

- 任何欄位標成隱藏的頂層鍵。
- 翻譯物件裡任何標成隱藏的可翻譯鍵。
- payload 式多對多關聯 `{ id, ...payload }` 元素裡任何標成隱藏的 payload 鍵——純 id 的元
  素本來就沒有 payload 可以遮。

除此之外的內容原封不動。

這層遮蔽只套用在對外的單筆版本讀取路徑；還原讀的是原始、未遮蔽過的快照，因為還原必須能把
隱藏欄位的值真正復原回去。因此一個隱藏值離開伺服器的唯一方式，是它對那一列資料造成的效
果，而不會出現在任何回應內容裡。

遮蔽套用在每一筆舊版本紀錄上，不只是最新的一筆。範例裡 `Article.InternalNote`（頂層）與
`ArticleTranslation.InternalSlug`（逐 locale）就是宣告成隱藏的欄位。

## 列出、檢視與還原

版本紀錄對外是三個 REST 端點：

- `GET /api/items/{collection}/{id}/revisions`——列出由新到舊排序的 metadata
  （`revisionNumber`、`operation`、`createdAt`、`createdBy`、`sourceRevisionNumber`），不
  含快照內容。
- `GET /api/items/{collection}/{id}/revisions/{n}`——回傳單筆版本紀錄，連同遮蔽過的
  `snapshot`，以結構化 JSON 而非字串形式呈現。
- `POST /api/items/{collection}/{id}/revisions/{n}/revert`——套用該筆快照，不需要帶
  body。

列出與檢視只需要這個集合一般的讀取授權，還原則需要一般的寫入授權，版本紀錄沒有自己專屬的
授權層級。一個沒開版本紀錄的集合，列表會回傳空陣列而不是 404，單筆檢視則是 404，未知的版
本編號或項目 id 也是 404。列表一律依版本編號排序，不是依建立時間。

GraphQL 從同一個開關加出對應的三個介面，不需要逐集合寫任何程式碼：一個版本列表欄位、一個
單筆版本欄位、一個還原用的 mutation，共用一個 `Revision` 型別，欄位跟 REST 一樣。GraphQL
列表欄位上的 `snapshot` 是 `null`。

後台的版本紀錄面板則是這三個 REST 端點的一層薄介面，不是走 GraphQL，包含列表、單筆快照檢
視與掛在項目表單上的還原動作；只有已經存過的項目、且集合開了版本紀錄時才會出現，還原動作
也只在呼叫端有這個集合的寫入授權時才會出現。面板上的操作標籤只有建立、更新、還原三種，丟
進垃圾桶或復原留下的紀錄會落到通用的預設標籤上。

建立後更新過一次的項目，列出它的版本紀錄只回傳 metadata，不含快照內容，由新到舊排序：

```text
$ GET /api/items/article/01a08c68-57d6-7f25-80e7-c42a2a1702a4/revisions
{"success":true,"data":[{"revisionNumber":2,"operation":"update","createdAt":"2026-09-10T17:40:44.397818","createdBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","sourceRevisionNumber":null},{"revisionNumber":1,"operation":"create","createdAt":"2026-09-10T17:40:43.741968","createdBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","sourceRevisionNumber":null}]}
HTTP_STATUS:200
```

快照本身要另外呼叫單筆端點才看得到。

還原會讀出目標版本的原始快照，先拿掉裡面的 `version` 鍵——避免拿一個過期的並行控制版本去
跟目前的列比對、平白產生衝突——再把結果透過跟一般寫入完全相同的更新路徑套用回去，標記成
`revert`。

還原本身也會另外多寫一筆新的 `revert` 版本紀錄，而不是把歷史往回轉：時間軸只能往前累加，
要撤銷一次還原，做法是再還原到更早的一個版本號。除此之外，還原是一次普通的寫入：一樣的寫
入授權與超級管理員規則、一樣的樂觀並行控制、一樣的項目回應形狀。

還原一筆快照裡帶 junction payload 的版本紀錄時，套用那些物件元素的方式跟直接寫入
payload 完全一樣，因此除了項目本身，也要有 junction collection 自己的寫入權限，細節見
[第 8 章：關聯](08-relations.md)。還原也是唯一一條容許多對多目標「快照擷取之後才被丟進垃圾
桶」的寫入路徑：它會把參照復原回去，而不是像其他寫入路徑那樣嚴格拒絕。

還原只會復原快照當初捕捉到的東西——自己的欄位、關聯狀態、每個 locale 的完整翻譯。系統管理欄
位與項目的軟刪除狀態不在快照裡，還原也就不會動它們。還原不會改動任何其他項目。

正因為還原是走跟一般更新完全一樣的路徑，對一個目前正在垃圾桶裡的項目做還原會直接得到
404——更新路徑讀取當前列時本來就會排除已經丟進垃圾桶的資料。正確的順序是先復原、再還原，
反過來行不通。

## 軟刪除：`ISoftDeletable`

`ISoftDeletable` 是一個不需要額外套件的標記介面，帶 `DateTime? DeletedAt` 與
`Guid? DeletedBy` 兩個成員，設計上呼應稽核介面「不需要屬性」的做法：`DeletedAt` 是 `null`
代表這一列還活著，丟進垃圾桶的當下由框架自己填上這兩個值。

框架自己的集合裡只有 `File` 實作它；範例的 `Article` 與 `Category` 也實作，而且兩個成員都
沒有另外標 `[SugarColumn]`，直接靠框架對可為 `null` 型別的推斷。

這兩個成員都沒有 `[CmsField]`，所以軟刪除狀態不算欄位 metadata 的一部分，既不會出現在項目
投影裡，也不能透過通用的項目 API 寫入。

底層是一道全域註冊的查詢過濾器，條件是「刪除時間為 null」，每個資料庫連線情境都會套用一
次。它涵蓋每一個對可軟刪除實體的查詢，不需要在呼叫端各自加程式碼：列表、單筆讀取、關聯展
開、跨關聯的 id 解析、多對多的存在性檢查，以及刪除限制式的檢查，預設都會排除已經丟進垃圾
桶的資料列。

真的需要看到已刪除資料的讀取，只會針對那一次查詢單獨解除這道過濾，而不是整層關掉——預設
看不到垃圾桶內容，才是出錯時比較安全的方向。會單獨解除這道過濾的情況包括：

- 明確要求含已刪除資料的單筆讀取。
- 列表與統計依 `deleted=` 參數決定要不要看垃圾桶。
- 清除操作自己遞迴尋找要一併清掉的資料時。
- 檔案刪除流程自己找出要清除項目時的內部查詢。

這道過濾器只影響查詢，不會套用到更新陳述式：丟進垃圾桶與復原這兩個寫入自己另外帶一段明確
的條件，不靠這層過濾器擋。它們都是一次以目前狀態為條件的原子更新——條件是刪除時間為 null
或不為 null——而不是先讀再寫，所以重複丟一個已在垃圾桶的項目、或復原一個本來就活著的項
目，影響的列數是零，而不是兩個呼叫互相競速。

對繼承 `AuditableEntity` 的集合，同一句更新也會順便把版本號往前推一格，所以拿著過期版本
號的呼叫端，遇到一列剛被丟進垃圾桶或剛復原的資料，一樣會正確地衝突失敗。

唯一索引碰到已在垃圾桶裡的資料列會出問題，框架目前也沒有任何機制可以避開：這道過濾器是查
詢層面的，不是索引本身的條件，所以一列已經在垃圾桶裡的資料仍然佔著它的唯一值，一筆新的、
活著的列想用同一個值就會被擋下，除非舊的那一列先被徹底清除。框架與範例目前都沒有在可軟刪
除的實體上宣告唯一索引，所以這個情況只有自己另外加唯一索引的專案才會遇到。

框架用來產生索引的只有欄位清單、是否唯一、唯一群組名稱，跟 `IndexName` 這幾樣輸入，沒有
任何「條件式」或「過濾式」索引的概念，所以一個只排除已刪除資料的局部唯一索引沒辦法透過框
架自己的建表流程表達，需要的話得自己寫一份資料庫遷移腳本。

## `DELETE` 與 `?purge`、復原

`DELETE /api/items/{collection}/{id}` 對一個可軟刪除的集合是丟進垃圾桶，對其他集合則是永
久刪除；帶 `?purge=true` 會強制走永久刪除這條路，而不是軟刪除的更新。沒有
軟刪除層的集合不管帶不帶這個參數都是永久刪除，因為它本來就沒有中間狀態可以停留。
`POST .../restore` 會替任何可軟刪除的集合清掉那兩個欄位。

清除在同一筆交易裡依序做這幾件事：

1. 檢查限制式的外鍵約束。
2. 把指向它的外鍵設成 `null`。
3. 遞迴清掉真正該連動刪除的資料。
4. 清掉它自己以及其他集合指向它的 junction 列。
5. 清掉翻譯的 sidecar 列。
6. 清掉它的版本紀錄。
7. 刪掉這一列本身。

項目端點只在這個參數的值完全等於 `true`（大小寫不拘）時才走永久刪除：對可軟刪除的集合，
`?purge=1` 或單純 `?purge` 都會被當成一般丟進垃圾桶，不會報錯。檔案端點走的是一般的參數
繫結，同樣的 `1` 在那邊反而算數，兩個介面在這裡並不一致。復原需要的是這個集合的刪除授
權，不是寫入授權。

重複丟進垃圾桶不會出錯：對一個已經在垃圾桶裡的項目再丟一次，一樣算成功，因為那一列確實存
在，只有未知的 id 才是 404；`DELETE` 成功回 204，失敗回 404，`restore` 成功回投影過的項
目，失敗回 404。

垃圾桶列表就是一般的列表帶上 `?deleted=only`，清除就是 `DELETE` 上的那個參數，兩者都不需
要另外的端點。復原只動那兩個欄位跟版本號，關聯、junction 列與翻譯在丟進垃圾桶時本來就沒
被動過，自然也沒有東西需要復原。

以下是完整的一次垃圾桶往返：丟進垃圾桶、用 `?deleted=only` 找到它、再復原（列表額外用
`filter[id][_eq]` 收斂到這一筆，因為開發用的資料庫裡還留著其他已經丟進垃圾桶的文章）：

```text
$ DELETE /api/items/article/01a08c68-5909-7513-8a9c-906f1fc22943

HTTP_STATUS:204

$ GET /api/items/article?deleted=only&filter[id][_eq]=01a08c68-5909-7513-8a9c-906f1fc22943
{"success":true,"data":[{"id":"01a08c68-5909-7513-8a9c-906f1fc22943","version":7,"status":"draft","publishedAt":null,"heroImageId":null,"regions":[],"audiences":[],"keywords":[],"attributes":null,"meta":{},"gallery":[],"faqs":[],"createdAt":"2026-09-10T17:40:43.913263","createdBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","updatedAt":"2026-09-10T17:40:43.913276","updatedBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","translations":{"en":{"title":"Scratch article","body":null,"seoTitle":null,"seoMetaDescription":null,"seoOgImageId":null,"seoOgImage":null}}}],"meta":{"total":1,"limit":25,"offset":0}}
HTTP_STATUS:200

$ POST /api/items/article/01a08c68-5909-7513-8a9c-906f1fc22943/restore
{"success":true,"data":{"id":"01a08c68-5909-7513-8a9c-906f1fc22943","version":8,"status":"draft","publishedAt":null,"heroImageId":null,"regions":[],"audiences":[],"keywords":[],"attributes":null,"meta":{},"gallery":[],"faqs":[],"createdAt":"2026-09-10T17:40:43.913263","createdBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","updatedAt":"2026-09-10T17:40:43.913276","updatedBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858"}}
```

`restore` 回傳的項目版本編號從 7 推到 8。`deletedAt` 從頭到尾都不在投影裡：垃圾桶狀態只能靠
`?deleted=` 查到，沒辦法從項目本身讀出來。

## `deleted=` 過濾器與權限

`deleted=` 接受三個值，用在列表、query 端點與單筆讀取上：`exclude`（預設，跟底層過濾器一
致）、`only`、`with`。值的比對不分大小寫，缺值或空字串當成 `exclude`，其他任何拼法都是
400，訊息會列出三個可接受的拼法：

```text
Query parameter 'deleted' must be exclude|only|with.
```

即使是 query 端點的 JSON 封裝形式，這個參數也一律從查詢字串讀，寫法是
`POST .../query?deleted=only`；`all`、`true`、`trash` 都不在這三個拼法之內。

要求 `exclude` 以外的值，需要的是這個集合的刪除授權，不只是讀取授權，這道檢查是刻意比一
般查詢更嚴格的：一列資料曾經被刪除這件事本身，就可能是只有讀取權限的呼叫端不該知道的資
訊。訊息是：

```text
Viewing deleted items requires delete permission.
```

`only` 與 `with` 都會解除最外層查詢的底層過濾，`only` 另外加上「刪除時間不為 null」的條
件；集合沒有軟刪除層時，這個參數對它沒有作用。GraphQL 用同名的三個大寫值當成 enum 參
數，套用一模一樣的授權門檻。

要留意的是，關聯篩選走的是另一條路：不管外層請求的 `?deleted=` 是什麼，關聯的子查詢一律
照常套用目標集合自己的軟刪除過濾，不會為它解除，所以就算正在看父層的垃圾桶，一筆已丟進垃
圾桶的關聯資料也不會滿足帶點號路徑或量詞式的篩選條件。

## 垃圾桶與版本紀錄的互動

一個集合同時開了軟刪除與版本紀錄時，丟進垃圾桶與復原才會各自留下一筆版本紀錄，寫在跟那次
原子更新相同的交易裡，也一樣有「真的影響到一列才記錄」這道閘門，一次沒有效果的丟入垃圾桶
不會留下任何東西。這筆快照記下的是丟進垃圾桶或復原那一刻的欄位值。

清除走的是完全不同的一條路：它是透過清除流程做的永久刪除，因此只有丟進垃圾桶才會留下一
筆刪除相關的版本紀錄，清除本身不會。清除會把這個項目全部的版本歷史一起清掉，讓一個永久刪
除的項目不留下無人能存取的孤兒快照；接了自己的儲存實作卻忘了接上這段清除邏輯時，框架會直
接丟出例外，逼出這個疏漏。

版本紀錄的列表與檢視完全不看軟刪除狀態：一個已經在垃圾桶裡的項目，它的歷史只需要這個集合
的讀取授權就能看到。
