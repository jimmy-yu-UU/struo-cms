# 21. 資料庫結構管理與升級

資料表怎麼被建立、既有資料表什麼時候會被改，以及核心本身的結構變動要怎麼傳到你的
fork——這一章把這三件事講清楚。

## 三層職責

資料表結構的變動分成三層，各自的職責、開關與適用環境都不一樣。

CodeFirst 建表：只要一個 entity 類別對應的資料表還不存在，不管哪一種後端、哪一種環境，
開機就會自動建出來，永遠開著，不能關。

結構同步：依 entity 類別跟既有資料表的結構差異，自動新增、修改甚至刪除欄位；只在
Development 生效，預設關閉，鍵名與型別見[第 4 章：設定參考](04-configuration.md)。它是
下一節要細談的、唯一可能悄悄動到既有資料的一層。

migration 腳本：套用你自己寫好、審查過的 `.sql` 檔案；所有環境都會執行，同樣預設關閉。
這是既有資料表在正式環境唯一該走的改動路徑。

三層完整對照、腳本怎麼寫、鍵名細節，見 `db/migrations/README.md`。

## 啟動順序

開機時，六個步驟固定按同一個順序跑：拍一張既有資料表的快照、建表、（Development 且開
啟時）結構同步、（設了路徑時）套用 migration 腳本、（Development）schema guard、植入資
料。順序不是隨機排的。

建表排第一，是因為 migration 腳本假設要改的資料表已經存在——`ALTER` 沒有東西可以改；結
構同步同樣要先有表可比對，才談得上跟 entity 類別的差異。schema guard 跟植入資料排在最
後，兩者都得看最終的資料表形狀：schema guard 要驗證的索引，得等前面所有可能建表、改表
的步驟都跑完才確定存在；植入資料只植入這次開機新建出來的表，太早跑會漏掉 migration 或
同步剛加出來的欄位。

## 一定成立的保證與一定不會發生的事

整個機制只有兩個保證，五種後端、任何環境都不例外。

第一個保證：只要一個 entity 類別對應的資料表還不存在，開機一定會建出來，這次新建的表也
才會被植入初始資料。「一律成立」講的是程式碼路徑一律成立，不是驗證證據一律成立——
PostgreSQL 是唯一真的拿實際資料庫驗證過的後端，其餘後端目前只是型別對應設計上支援。

第二個保證，反過來看：一張已經存在的資料表，唯一會被自動改動的兩種方式，是明確打開的結
構同步（僅 Development），或是一支經過審查、由 migration runner 套用的腳本；兩者都是主
動選擇，不會有第三種路徑讓既有資料表在不知情的狀況下被改掉。

## 結構同步的危險情境

> 結構同步只比較 entity 類別和既有資料表兩個結構的差異，看不出你的意圖——改名跟「砍一
> 欄、加一欄」在它眼裡是同一件事；凡是會動到既有資料的結構改動，一律得走 migration。

以下九種情境，都是這種「看不出意圖」在實際場景裡的樣子。

1. **改欄位名稱** — 同步讀成「舊屬性消失、新屬性出現」，對舊欄位下 `DROP COLUMN`、對新
   欄位下 `ADD COLUMN`，資料永久遺失；正確做法是先寫一支 `RENAME COLUMN` 的 migration，
   之後才改 entity 類別。
2. **移除屬性** — 直接 `DROP COLUMN`，資料跟著消失；確認這欄真的不再需要之後，用一支明
   確的 migration 在正式環境執行。
3. **欄位型別限縮** — 依後端而定：直接失敗，或悄悄截斷資料；正確做法分三步——加新欄
   位、回填並驗證、最後才切換到新欄位並砍掉舊的。
4. **對已有資料的表加 `NOT NULL`** — `ALTER` 直接失敗，啟動中止；三步式 migration：先
   加可為 null 的欄位、回填、最後才補上 `NOT NULL`。
5. **對有重複值的欄位加 `UNIQUE`** — `ALTER` 一樣失敗，啟動中止；migration 先去重（這
   是一次資料操作），再補上限制。
6. **拆分或合併欄位** — 結構化的差異表達不出這種意圖，結果永遠是資料遺失或欄位空著；這
   種改動永遠只能靠 migration。
7. **SQLite 上刪欄位** — 這個旗標（`SqliteCodeFirstEnableDropColumn`）確實存在，只是
   `SqlSugarClientFactory` 沒有打開它。打開後不是統一解鎖：普通欄位會被悄悄刪掉，SQLite
   原生擋下的欄位（主鍵、唯一索引、一般索引、`CHECK` 或外鍵參照）會讓 `ALTER TABLE` 失
   敗，啟動整個中止。
8. **多副本同時啟動** — 每個副本各自算出、各自執行自己的結構差異，等於好幾個副本同時搶
   著改同一張表；跟 migration runner 沒有互斥鎖是同一種風險，同一種做法：先讓一個副本
   上線，其餘副本晚一步跟上，或者另外開一個一次性的 job 來做。
9. **看不到將要跑的 DDL** — 同步是啟動當下依照那一刻的程式碼即時算出來的，沒辦法事先
   預覽；這正是結構同步從來不該在正式環境開啟的核心原因。

## 撰寫 migration

檔案怎麼命名、哪些 SQL 該用哪些該避免、為什麼不用做到冪等、追蹤方式、時區慣例——這些撰
寫規則的唯一權威版本是 `db/migrations/README.md`，這裡不重複。

部署時真正會踩到的，只有兩點。

第一，沒有互斥鎖：好幾個副本同時針對同一個 `Database:MigrationsPath` 啟動，可能同時嘗
試套用同一個還沒套用過的檔案；建表跟結構同步也有同樣的風險。分階段部署時，先讓一個副本
套用完，或另外開一個一次性的 job 來跑，其餘副本再上線。

第二，目錄本身要存在：`db/migrations/` 底下只放一份 `README.md`，不附任何 `.sql` 檔案；
如果部署流程只是「有什麼就複製什麼」，並不保證這個目錄會出現在部署出去的映像裡。
`Database:MigrationsPath` 設定了、目錄卻不存在時，啟動會丟出
`DirectoryNotFoundException` 並以代碼 `1` 結束。

## 開發期的結構防護

`SchemaGuard` 只在 Development 執行，跑在建表、結構同步、migration 腳本之後：它驗證兩
件事真的存在——`revisions` 資料表上 `(collectionname, itemid, revisionnumber)` 的複合
唯一索引，以及每一個有翻譯附屬表的集合，其附屬表上 `(fk, locale)` 的唯一索引（附屬表本
身可以不存在，但如果存在，索引就得存在）。缺了任何一個，就丟出一個講清楚缺什麼的例外。

它只認 PostgreSQL 跟 SQLite；MySql、SqlServer、Oracle 直接跳過，什麼都不驗證。它是開發
期的快速失敗機制，抓的是「這次改動漏了該有的索引」，不是正式環境的安全網——正式環境根
本不會執行它。

## 核心的四個 raw SQL 例外

整個系統的資料庫存取都得經過 SqlSugar，只留下四個刻意的例外會組字串 SQL，見
[第 2 章：系統架構](02-architecture.md)。這四個例外分別為什麼存在：

- `db/migrations/*.sql` 腳本——這是規則本身，migration 存在的意義就是讓 fork 自己寫
  SQL。
- `SchemaGuard` 的唯讀 catalog 查詢——索引沒辦法靠名稱找（不同後端、不同建立路徑取的名
  字不一樣），只能直接查 `pg_indexes`／`sqlite_master` 這類系統目錄，而且只在
  Development 執行、只讀不寫。
- 關聯篩選下推用的子查詢包裝——四種組好的字串形式，是把「篩選子集合」這種查詢語意轉成
  SQL 子查詢時，運算式樹表達不出來的部分。
- `OrderByExpressionBuilder` 的 `ORDER BY` 文字——三種按欄位組出來的形式，同樣是運算式
  樹表達不出的排序語意。

四個例外都不牽涉寫入既有資料表的結構，跟本章前面談的三層職責是兩回事。

## 跨 fork 升級核心

核心不附任何 `.sql` 腳本，建表又只做「補齊缺的表」這一件事，所以核心的結構變動沒有辦法
自動送到部署裡：一次 release 改了核心的資料表結構，不會有任何機制幫你的 fork 把既有資
料表跟著改掉。

核心的結構變動寫在 release notes 裡；照著改的，是你自己針對實際跑的後端寫一支 `ALTER`
腳本，走前面說的 migration 這條路。

打開結構同步，對著一份正式環境資料庫的副本跑一次，可以把它算出來的差異當作「這次升級大
概要改哪些欄位」的提示——但只能當提示，不能當成直接拿去執行的計畫：本章列的九種危險情
境，在這份差異上一樣成立。完整程序見 `db/migrations/README.md`。
