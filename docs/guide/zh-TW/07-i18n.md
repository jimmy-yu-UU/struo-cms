# 7. 多語內容

一個欄位要怎麼替每種語言分別存一份內容，API 與後台又怎麼把這些翻譯呈現出來，是這一章的主題。

## 兩種 locale：介面語言與內容語言

多語裡有兩個彼此獨立的概念。內容語言決定一次讀寫作用在哪一份可翻譯欄位的副本，來源是
`languages` 資料表、讀取時的 `?locale=`，以及寫入時 `translations` 物件裡的 locale 鍵。介面語
言決定後台自己的介面文字顯示哪一種語言，完全在前端處理，不會送到 API，也不會碰
`languages` 資料表。

## `languages` 資料表與 `GET /api/languages`

內容語言是框架自帶 `Language` entity 裡的一列，這個 entity 本身也是 `System` 群組下的一個
`[CmsCollection]`，除了自己的讀取端點，也能透過一般的項目 API（`/api/items/language`）編輯。
每一列帶 `code`、`name`、`isDefault`、`enabled`、`sort` 五個欄位。全新安裝預設種好兩個已啟用
的語言：`en`（`isDefault`）與 `zh-TW`。

`GET /api/languages` 對任何已登入的呼叫端開放，不限管理員，只回傳已啟用的語言，投影成
`code`、`name`、`isDefault`。預設語言依序解出：已啟用且 `isDefault` 的那一列，否則
`sort` 最小的已啟用列，否則退回字面值 `"en"`；`enabled` 的比對不分大小寫。已啟用的語言集合
在同一個請求範圍內只算一次，讀寫時的每一次 locale 檢查都經過同一個 provider，所以停用某個
語言列，下一個請求就會生效，不用重啟。

`language` 列的 `code` 寫入時會做字元集驗證，跟讀取時用的規則一樣：`Language code '{code}'
contains invalid characters. Codes must match [A-Za-z0-9_-]{1,35}.`

## 讓欄位可翻譯

一個欄位變成逐語言存放，靠的是把它宣告在 `[CmsTranslations]` 指到的翻譯 sidecar 型別上，不
是在父層欄位上把 `Translatable` 設成 `true`。掃描 sidecar 時，掃描器會直接把每個 sidecar 欄
位的 `Translatable` 蓋成 `true`，不管屬性本身寫了什麼；出廠的 sidecar 也沒有一個自己手動設
過這個旗標。反過來，在父層的 `[CmsField]` 上手寫 `Translatable = true` 是無效的：它會被原封
不動抄進 `FieldMetadata`，背後沒有任何 sidecar，必填檢查與翻譯覆蓋層都會跳過這種欄位，結果
是 metadata 上看起來可翻譯，實際上永遠不會逐語言解析——不要在父層欄位上設這個旗標。

掃描器會把 sidecar 的每個欄位併入父集合自己的欄位清單，所以一個可翻譯欄位跟一般欄位一樣可
以篩選、搜尋、排序，差別只在它會對到 sidecar 資料表、在有效查詢 locale 下解析，而且是下推成
子查詢，不是先在記憶體裡解出來。有效查詢 locale 是 `?locale=` 給了就用，沒給就用預設語言，
所以完全不帶 `?locale=` 一樣能對可翻譯欄位篩選；某個 locale 沒有翻譯列的項目，篩選時會被排
除，排序時當作 `NULL`。

有六個介面完全不能設為可翻譯，[第 6 章：欄位型別與編輯介面](06-field-types.md)已經列出——這
表示一個逐語言的多選或 repeater 是做不到的。

## 翻譯附屬資料表

sidecar 是一個普通的 SqlSugar entity，本身不是 `[CmsCollection]`，靠父層一個被忽略的清單屬
性掛上 `[CmsTranslations(typeof(TSidecar))]` 連起來。範例的 `Article` 這樣宣告：

```csharp
[CmsTranslations(typeof(ArticleTranslation))]
[SugarColumn(IsIgnore = true)]
public List<ArticleTranslation> Translations { get; set; } = [];
```

sidecar 型別必須宣告四樣東西，否則啟動時掃描失敗，各自有自己的 `MetadataException`：一個叫
`Id` 的屬性、一個依 `{ParentTypeName}Id` 命名慣例的外鍵、一個名字剛好是 `Locale` 的 `string`
屬性，以及至少一個 `[CmsField]`。`ArticleTranslation` 是完整的樣子：

```csharp
using SqlSugar;
using Struo.Domain.Metadata.Attributes;
using Struo.Domain.Metadata.Enums;

namespace Struo.Sample.Blog;

[SugarTable("article_translations")]
public sealed class ArticleTranslation : Struo.Domain.Seo.SeoTranslation
{
    [SugarColumn(IsPrimaryKey = true, IsIdentity = true)] public long Id { get; set; }
    // ArticleId/Locale carry no unique attribute here: SqlSugarClientFactory's EntityService hook reads
    // this table's [CmsTranslations] metadata through TranslationSidecarIndexPolicy and adds the
    // composite unique (articleid, locale) to the generated column model at CodeFirst time; SchemaGuard
    // re-checks the resulting index in Development. This sample schema is not part of core, so a
    // downstream fork keeping this entity gets the index for free on a fresh CodeFirst table, and only
    // needs to write its own migration for a table that already exists in the target database.
    public Guid ArticleId { get; set; }
    public string Locale { get; set; } = "";
    [CmsField(Label = "Title", Interface = FieldInterface.Text, Required = true, Searchable = true, Sortable = true, Sort = 1, Group = "Content")]
    public string Title { get; set; } = "";
    [SugarColumn(IsNullable = true)]
    [CmsField(Label = "Body", Interface = FieldInterface.RichText, Sort = 2, Group = "Content")]
    public string? Body { get; set; }
    // Hidden per-locale field (a redaction-test fixture): must be redacted from `translations.{locale}` in any
    // snapshot returned externally, but preserved for RevertAsync (see Article.InternalNote).
    [SugarColumn(IsNullable = true)]
    [CmsField(Label = "Internal Slug", Interface = FieldInterface.Text, Hidden = true, Sort = 3, Group = "Content")]
    public string? InternalSlug { get; set; }
    // SeoTitle / SeoMetaDescription / SeoOgImageId inherited from SeoTranslation.
    // SqlSugar EntityService hook maps Nullable<T> → IsNullable=true for all backends,
    // so no [SugarColumn(IsNullable=true)] override is needed here.
}
```

保持一個父層最多一列翻譯的 `(fk, locale)` 唯一索引不用自己宣告，hook 會自動加上：CodeFirst
建表前，同一個 hook 會讀父層的 `[CmsTranslations]` metadata，把這個唯一索引群組蓋到外鍵與
`Locale` 兩個欄位上。已經存在、還沒有這個索引的 sidecar 資料表不會被追加索引，這種情況要走
一般的 migration；唯一的例外是開啟 `Database:AutoSyncSchema` 的 Development 環境，它的完整
同步會嘗試補上索引，如果資料表已經有重複的 `(fk, locale)` 資料，啟動就會直接失敗，把髒資料
攤開來而不是蓋過去。Development 另外有一道啟動檢查，依唯一性與欄位覆蓋範圍（不是看名字）
重新確認每個設定過的 sidecar 索引，缺了就丟出說明清楚的錯誤；這道檢查只在 PostgreSQL 與
SQLite 上跑，其他三種後端會直接略過，等於完全沒有這道啟動檢查。自己組 SqlSugar client、繞
過框架 DI 註冊的 fork，得自己把 sidecar 政策傳進去——漏了會悄悄退回空政策，每張 sidecar 資
料表都不會有唯一索引，而且當下不會報錯。

可翻譯欄位的 `MaxLength` 是逐 locale 檢查的，錯誤訊息會點名是哪個 locale：`Field '{name}'
exceeds maximum length {n} for locale '{locale}'.`

## 逐語言 SEO

`SeoTranslation` 是一個抽象基底類別，sidecar 可以繼承它拿到三個現成的 `Group = "SEO"` 欄
位：`SeoTitle`（`Text`）、`SeoMetaDescription`（`Textarea`）、`SeoOgImageId`（`Image`）。它
不掛任何 `[SugarColumn]`，因為 domain 專案本身不依賴任何套件。SEO 只有逐語言這一種形式，沒
有父層可以退回的共用版本。

## 預設語言與寫入規則

建立時，預設語言的翻譯是必要的：`translations` 鍵缺席、值不是物件、物件是空的，或物件完全
沒提到預設語言的代碼，都會用同一句訊息拒絕：`A translation for the default locale '{code}'
is required.` 父層的新增與翻譯同步在同一個交易裡，拒絕會把整筆寫入一起回滾。

```text
$ POST /api/items/article
body:
{"status":"draft"}
{"success":false,"error":{"code":"BAD_USER_INPUT","message":"A translation for the default locale 'en' is required."}}
HTTP_STATUS:400
```

更新時這條規則放鬆：`translations` 缺席或不是物件都當成沒有要動翻譯的部分更新，可以只更新
父層欄位，或只更新一個非預設語言，不用每次都補齊全部語言。存在但未啟用的 locale 鍵，讀寫都
用同一句話拒絕：`Unknown or disabled locale '{locale}'.`；locale 代碼在檢查是否啟用之前就先
做字元集驗證，必須符合 `[A-Za-z0-9_-]{1,35}`，把 `?locale=` 上的 SQL 特殊字元注入路徑先擋
掉。

某個 locale 物件裡出現不是該 sidecar 自己可翻譯欄位的鍵，會被拒絕：`Field '{name}' is not a
translatable field of '{collection}'.`；sidecar 上標了 `Required` 的可翻譯欄位，每一個有提
供的 locale 都要非空，不只預設語言：`Required translation field '{name}' is missing for
locale '{locale}'.`。一個 locale 的值本身也必須是物件：`Translation for locale '{locale}'
must be an object.`

寫入一個 locale 會整列替換：同步邏輯先刪掉那個 locale 既有的列，再插入一列新的，所以本次沒
提到的欄位會落到 sidecar 屬性自己的初始值——`ArticleTranslation.Title` 這種不可為 null 的
`string` 會變成 `""`，`string?` 會變成 `null`，不是統一清成 `null`。沒被提到的 locale 完全
不受影響。逐 locale 的區域更新是以整個 locale 為單位，不是以欄位為單位——只送
`{"en": {"title": "x"}}` 會把 `en` 其他可翻譯欄位一起清成各自的屬性預設值。同一次寫入裡兩個
只差大小寫的 locale 鍵會合併，後面的贏；locale 對映本身不分大小寫。

## REST 與 GraphQL 回應裡的翻譯

有 sidecar 的集合，投影後的每一列一定帶 `translations` 物件，是在自己欄位投影完之後才接上
去的，所以就算用了 `fields=` 也不會不見。沒有 `?locale=` 時，裡面是每個有翻譯列的 locale，
以 locale 代碼為鍵：

```text
$ GET /api/items/article/01a08c68-57d6-7f25-80e7-c42a2a1702a4
{"success":true,"data":{"id":"01a08c68-57d6-7f25-80e7-c42a2a1702a4","version":0,"status":"draft","publishedAt":null,"heroImageId":null,"regions":[],"audiences":[],"keywords":[],"attributes":null,"meta":{},"gallery":[],"faqs":[],"createdAt":"2026-09-10T17:40:43.607052","createdBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","updatedAt":"2026-09-10T17:40:43.607133","updatedBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","translations":{"en":{"title":"Getting started with StruoCMS","body":"<p>Run the API and the admin SPA.</p>","seoTitle":null,"seoMetaDescription":null,"seoOgImageId":null,"seoOgImage":null},"zh-TW":{"title":"開始使用 StruoCMS","body":"<p>先把 API 與後台跑起來。</p>","seoTitle":null,"seoMetaDescription":null,"seoOgImageId":null,"seoOgImage":null}}}}
HTTP_STATUS:200
```

帶了 `?locale=` 之後，這個物件只會剩下那一個 locale，父層完全沒有該 locale 的翻譯列時是空
物件 `{}`，不是缺一個鍵，也不是 `null`：

```text
$ GET /api/items/article/01a08c68-58a8-78cd-82cc-c80d609530c6?locale=zh-TW
{"success":true,"data":{"id":"01a08c68-58a8-78cd-82cc-c80d609530c6","version":0,"status":"draft","publishedAt":null,"heroImageId":null,"regions":[],"audiences":[],"keywords":[],"attributes":null,"meta":{},"gallery":[],"faqs":[],"createdAt":"2026-09-10T17:40:43.817217","createdBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","updatedAt":"2026-09-10T17:40:43.817477","updatedBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","translations":{}}}
HTTP_STATUS:200
```

`?locale=` 是完全沒有退路的嚴格篩選：缺翻譯的 locale 就是沒有這個鍵，不會退回預設語言的
值，也不會給 `null` 佔位——前端自己要處理鍵不存在的情形。可翻譯欄位的值不會出現在父層那一
列：投影器對這種欄位完全不產生頂層鍵，唯一讀得到的地方就是 `translations` 底下。名字以
`Id` 結尾的可翻譯 `Image`／`File`／`Files` 欄位，locale 物件裡另外會有一個去掉 `Id` 尾巴的
解析鍵——`heroImageId` 同時會有 `heroImage`，放解析出來的檔案列或 `null`；解析需要對 `file`
的讀取授權，沒有授權時這個鍵是 `null`，原始 id 仍然會送出。名字不是以 `Id` 結尾的欄位不會
有這個解析鍵。`Hidden` 的可翻譯欄位連名字帶值都不外洩：翻譯覆蓋層會把它從每個 locale 物件
裡拿掉，schema 也會把它從集合的 `translation.fields` 清單裡拿掉。

GraphQL 讀翻譯是一個清單，不是一張映射表：有 sidecar 的集合會多一個
`translations: [Translation!]`，共用的 `Translation` 型別是 `{ locale: String!, fields:
Any! }`，`fields` 是通用 JSON 純量，放那個 locale 的欄位映射。寫入翻譯走的是每個集合自己的
型別化輸入，不是通用映射：每個可翻譯欄位對應一個輸入欄位，包成 `{ locale, fields }`，掛在每
個 create／update mutation 上；resolver 把這個清單折疊成跟 REST 一樣、以 locale 為鍵的物
件，同一個 locale 重複出現時後面的贏。可翻譯的父層欄位本身會從 GraphQL 的 create／update 輸
入型別裡排除，型別化的翻譯輸入是那裡唯一能寫入的方式。

## 後台的語言分頁與完成度

只有集合真的有可翻譯欄位時，後台才會顯示語言分頁，每個已啟用的語言各一個分頁，就算只啟用
一種語言也一樣；預設語言的分頁會多一個星號標記。每個分頁的完成度圓點，只在已啟用的語言超
過一種、而且集合有可翻譯欄位時才會出現，所以單一語言的安裝就算有可翻譯欄位，看到的也是沒
有圓點的一個分頁。

一個 locale 的圓點，只要它任何一個可翻譯欄位有非空值就會亮起——非空的去除空白字串、非空
陣列，或任何其他非 `null` 的值，數字（含 `0`）跟布林（含 `false`）都算有內容。這純粹是前端
根據已載入的表單資料算出來的訊號，不是驗證結果，跟伺服器端逐 locale 的 `Required` 規則沒有
關係。

表單只會用預設語言抓一次項目，所以每個非預設分頁一開始都是空的，不管資料庫裡實際存了什
麼；儲存時表單只送有內容的 locale，這正是沒被打開過的分頁不會被清空的原因——改動這兩者中的
一個而不動另一個會讓兩者對不起來。表單的建立與更新規則不一樣：建立時就算整個空白，預設語
言還是會送出，非預設語言整個空白就跳過；更新時整個空白的 locale 都跳過，包含預設語言。可翻
譯欄位的必填標記與前端錯誤訊息只在預設語言的分頁上渲染，非預設語言就算真的少了必填翻譯，
表單本身不會先標出來，要等伺服器拒絕。
