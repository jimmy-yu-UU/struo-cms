# 7. 多語內容

一個欄位要怎麼替每種語言分別存一份內容，API 與後台又怎麼把這些翻譯呈現出來，是這一章的主題。

## 兩種 locale：內容語言與介面語言

多語裡有兩個彼此獨立的概念：

- 內容語言決定一次讀寫作用在哪一份可翻譯欄位的副本，來源是 `struo_languages` 資料表、讀取時的
  `?locale=`，以及寫入時 `translations` 物件裡的 locale 鍵。
- 介面語言只決定後台介面文字的語言，全部在前端處理，透過 `UiLanguageSwitcher` 元件切換，選定的
  語言不會送到 API，也不會碰 `struo_languages` 資料表。可選的語言是 SPA 裡登錄的訊息目錄，不是
  `Localization` 區段或那張資料表，兩個集合各自獨立。

## 語言資料表與 `GET /api/languages`

內容語言是框架自帶 `Language` entity 裡的一列，這個 entity 本身也是 `System` 群組下的一個
`[CmsCollection]`，除了自己的讀取端點，也能透過一般的項目 API（`/api/items/language`）編輯。
每一列帶 `code`、`name`、`isDefault`、`enabled`、`sort`。核心的植入 migration `SeedCoreData`
在第一次 `migrate` 或 `MigrateOnStartup` 時依 `Localization` 設定種入語言（見
[第 4 章：設定參考](04-configuration.md)）；出貨的設定是 `en`（`isDefault`）與 `zh-TW`。之後這
張表就是唯一的來源，設定不再被讀取。

`GET /api/languages` 對任何已登入的呼叫端開放，不限管理員，只回傳已啟用的語言，投影成
`code`、`name`、`isDefault`。預設語言依序解出：

1. 已啟用且 `isDefault` 的那一列。
2. 否則 `sort` 最小的已啟用列。

一個已啟用的語言都沒有時，需要預設語言的請求會失敗；正常情況下走不到這裡，因為寫入 `language`
集合時有三條規則擋著：`code` 不分大小寫唯一、至少一列啟用、啟用列裡恰好一列是預設。違反任何一條
的建立、更新或刪除都會整筆回滾並回 400：`Language code '{code}' already exists.`、
`At least one language must remain enabled.`、`Exactly one enabled language must be the default.`。

語言代碼的比對不分大小寫，儲存與回傳都用語言列設定的寫法：寫入時的 `ZH-tw` 鍵、讀取時的
`?locale=ZH-tw`，都會對應到 `zh-TW`。已啟用的語言集合在同一個請求範圍內只算一次，讀寫時的每一次
locale 檢查都經過同一個 provider，所以停用某個語言列，下一個請求就會生效，不用重啟。

## 讓欄位可翻譯

一個欄位變成逐語言存放，靠的是把它宣告在 `[CmsTranslations]` 指到的翻譯 sidecar 型別上，不
是在父層欄位上把 `Translatable` 設成 `true`。宣告在 sidecar 上的欄位一律是可翻譯的，
`Translatable` 寫不寫都一樣。

反過來，在父層的 `[CmsField]` 上手寫 `Translatable = true` 是無效的：背後沒有任何 sidecar，
必填檢查會跳過這種欄位，`MaxLength` 與各介面的驗證器也一樣跳過它，但寫入內容仍會綁定進來，
讀取時也不會處理它，結果是 metadata 上看起來可翻譯，實際上永遠不會逐語言解析。

掃描器會把 sidecar 的每個欄位併入父集合自己的欄位清單，所以一個可翻譯欄位跟一般欄位一樣可
以篩選、搜尋、排序，差別只在它會對到 sidecar 資料表，在有效查詢 locale 下解析。有效查詢
locale 是 `?locale=` 給了就用，沒給就用預設語言，所以完全不帶 `?locale=` 一樣能對可翻譯欄位
篩選；某個 locale 沒有翻譯列的項目，篩選時會被排除，排序時當作 `NULL`。

`MultiSelect`、`CheckboxGroup`、`Tags`、`KeyValue`、`Files`、`Repeater` 這六個介面不能設為
可翻譯，在其中任何一個上寫 `Translatable = true`，啟動時就是 `MetadataException`：`Field
'{name}' uses interface '{Interface}', which cannot be translatable.`。`Json` 刻意不在這一
組裡，所以做不出逐語言的多選或 repeater，但逐語言的原始 JSON 可以。

## 翻譯附屬資料表

這張逐語言的附屬資料表（以下沿用 sidecar 的說法）是一個普通的 SqlSugar entity，本身不是
`[CmsCollection]`，靠父層一個被忽略的清單屬性掛上 `[CmsTranslations(typeof(TSidecar))]` 連
起來。範例的 `Article` 這樣宣告：

```csharp
[CmsTranslations(typeof(ArticleTranslation))]
[SugarColumn(IsIgnore = true)]
public List<ArticleTranslation> Translations { get; set; } = [];
```

sidecar 型別必須宣告四樣東西，少了下面任何一項，啟動時掃描就會失敗，各有自己的
`MetadataException`：

- 一個叫 `Id` 的屬性。
- 一個依 `{ParentTypeName}Id` 命名慣例的外鍵。
- 一個名字剛好是 `Locale` 的 `string` 屬性。
- 至少一個 `[CmsField]`。

`ArticleTranslation` 是完整的樣子：

```csharp
using SqlSugar;
using Struo.Domain.Metadata.Attributes;
using Struo.Domain.Metadata.Enums;

namespace Struo.Sample.Blog;

[SugarTable("article_translations")]
public sealed class ArticleTranslation : Struo.Domain.Seo.SeoTranslation
{
    [SugarColumn(IsPrimaryKey = true, IsIdentity = true)] public long Id { get; set; }
    public Guid ArticleId { get; set; }
    public string Locale { get; set; } = "";
    [CmsField(Label = "Title", Interface = FieldInterface.Text, Required = true, Searchable = true, Sortable = true, Sort = 1, Group = "Content")]
    public string Title { get; set; } = "";
    [SugarColumn(IsNullable = true)]
    [CmsField(Label = "Body", Interface = FieldInterface.RichText, Sort = 2, Group = "Content")]
    public string? Body { get; set; }
    [SugarColumn(IsNullable = true)]
    [CmsField(Label = "Internal Slug", Interface = FieldInterface.Text, Hidden = true, Sort = 3, Group = "Content")]
    public string? InternalSlug { get; set; }
}
```

`(fk, locale)` 唯一索引不用在 entity 上宣告：`make:migration --entity` 替 sidecar 產生的
migration 會呼叫 `CreateTranslationUniqueIndex`，建出名為 `ux_<資料表>_fk_locale` 的索引，一個
父層在同一個 locale 下最多只會有一列翻譯。核心的 `file_translations` 也是這樣建的。

已經存在、還沒有這個索引的 sidecar 資料表，要自己寫一支 migration 補上。表裡已經有重複的
`(fk, locale)` 資料時，建索引會失敗，要先去重。

Development 啟動時的結構檢查與 `migrate:check` 都會確認每張 sidecar 資料表真的有這個唯一索引，
缺了就報錯並點名該資料表。這道檢查涵蓋 PostgreSQL、SQL Server、MySQL／MariaDB 與 SQLite；
Oracle 以警告跳過。

## 逐語言 SEO

`SeoTranslation` 是一個抽象基底類別，sidecar 可以繼承它拿到三個現成的 `Group = "SEO"` 欄
位：`SeoTitle`（`Text`）、`SeoMetaDescription`（`Textarea`）、`SeoOgImageId`（`Image`）。SEO
只有逐語言這一種形式，沒有父層可以退回的共用版本。

## 預設語言與寫入規則

建立時一定要帶預設語言的翻譯，少了整筆回滾：

```text
$ POST /api/items/article
body:
{"status":"draft"}
{"success":false,"error":{"code":"BAD_USER_INPUT","message":"A translation for the default locale 'en' is required."}}
HTTP_STATUS:400
```

`translations` 缺席、不是物件、是空物件，或沒提到預設語言，都是同一個 400。

更新時這條規則放鬆：`translations` 缺席或不是物件都當成沒有要動翻譯的部分更新，可以只更新
父層欄位，或只更新一個非預設語言，不用每次都補齊全部語言。還沒存過的 locale 鍵會插入成新的一列。存在但未啟用的 locale
鍵，讀寫都用同一句話拒絕：`Unknown or disabled locale '{locale}'.`

讀取時，locale 代碼在檢查是否啟用之前先做字元集驗證，必須符合 `[A-Za-z0-9_-]{1,35}`，順便
把 `?locale=` 上的注入字元擋在查詢之外；寫入時同一項驗證套用在 `translations` 物件的 locale
鍵上。

可翻譯欄位的 `MaxLength` 是逐 locale 檢查的，錯誤訊息會點名是哪個 locale：`Field '{name}'
exceeds maximum length {n} for locale '{locale}'.`

一個 locale 物件本身還有三條驗證規則：

- 出現不是該 sidecar 自己可翻譯欄位的鍵，會被拒絕：`Field '{name}' is not a translatable field
  of '{collection}'.`
- sidecar 上標了 `Required` 的可翻譯欄位必須非空。建立時，每一個有提供的 locale 都要帶，不只預設
  語言；更新時，檢查的是已存的值合併本次送來的值，所以已經有這個欄位的 locale 可以不再送：
  `Required translation field '{name}' is missing for locale '{locale}'.`
- 一個 locale 的值本身也必須是物件：`Translation for locale '{locale}' must be an object.`

更新一個 locale 是逐欄位合併：本次有送的欄位換成新值，沒送的欄位保留已存的值，明確送 `null`
則清空。只送 `{"en": {"title": "x"}}` 只會改 `en` 的標題，其他都不動。

沒被提到的 locale 完全不受影響。靠「不送就清掉」來清欄位的呼叫端，要改成明確送 `null`。

缺必填翻譯是 `400 BAD_USER_INPUT`，`error.details` 每個 locale 的每個缺漏欄位各一筆，每筆帶
`field`、`message` 與 `locale`；`message` 文字就是上面那一句。見
[第 12 章](12-rest-conventions.md#驗證錯誤的-details)。

```json
{"success":false,"error":{"code":"BAD_USER_INPUT","message":"Required translation field 'title' is missing for locale 'zh-TW'.","details":[{"field":"title","message":"Required translation field 'title' is missing for locale 'zh-TW'.","locale":"zh-TW"}]}}
```

同一次寫入裡兩個只差大小寫的 locale 鍵會合併，後面的贏；locale 對映本身不分大小寫，存下的是設定的寫法。

換預設語言只是把另一列標成 `isDefault`：既有項目若沒有新預設語言的翻譯列，在不帶 `?locale=` 的
查詢裡篩選時會被排除、排序時當作 `NULL`，建立新項目時也必須附上新預設語言的翻譯。沒有工具會自動
補上這些翻譯列，換之前先自己回填。

## REST 與 GraphQL 回應裡的翻譯

### REST

有 sidecar 的集合，投影後的每一列一定帶 `translations` 物件，是在自己欄位投影完之後才接上
去的；就算用了 `fields=`，`translations` 也不會被篩掉。沒有 `?locale=` 時，裡面是每個有翻譯
列的 locale，以 locale 代碼為鍵：

```text
$ GET /api/items/article/01a08c68-57d6-7f25-80e7-c42a2a1702a4
{"success":true,"data":{"id":"01a08c68-57d6-7f25-80e7-c42a2a1702a4","version":0,"status":"draft","publishedAt":null,"heroImageId":null,"regions":[],"audiences":[],"keywords":[],"attributes":null,"meta":{},"gallery":[],"faqs":[],"createdAt":"2026-09-10T17:40:43.607052Z","createdBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","updatedAt":"2026-09-10T17:40:43.607133Z","updatedBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","translations":{"en":{"title":"Getting started with StruoCMS","body":"<p>Run the API and the admin SPA.</p>","seoTitle":null,"seoMetaDescription":null,"seoOgImageId":null,"seoOgImage":null},"zh-TW":{"title":"開始使用 StruoCMS","body":"<p>先把 API 與後台跑起來。</p>","seoTitle":null,"seoMetaDescription":null,"seoOgImageId":null,"seoOgImage":null}}}}
HTTP_STATUS:200
```

兩個 locale 各一份，鍵就是 locale 代碼。

帶了 `?locale=` 之後，這個物件只會剩下那一個 locale，父層完全沒有該 locale 的翻譯列時是空
物件 `{}`，不是缺一個鍵，也不是 `null`：

```text
$ GET /api/items/article/01a08c68-58a8-78cd-82cc-c80d609530c6?locale=zh-TW
{"success":true,"data":{"id":"01a08c68-58a8-78cd-82cc-c80d609530c6","version":0,"status":"draft","publishedAt":null,"heroImageId":null,"regions":[],"audiences":[],"keywords":[],"attributes":null,"meta":{},"gallery":[],"faqs":[],"createdAt":"2026-09-10T17:40:43.817217Z","createdBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","updatedAt":"2026-09-10T17:40:43.817477Z","updatedBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","translations":{}}}
HTTP_STATUS:200
```

這是另一篇文章，沒有 zh-TW 的翻譯列，所以 `translations` 回來是空物件，不會退回預設語言。

`?locale=` 是完全沒有退路的嚴格篩選：缺翻譯的 locale 就是沒有這個鍵，不會退回預設語言的
值，也不會給 `null` 佔位，呼叫端自己要處理鍵不存在的情形。

可翻譯欄位的值不會出現在父層那一列：投影器對這種欄位完全不產生頂層鍵，唯一讀得到的地方就
是 `translations` 底下。

名字以 `Id` 結尾的可翻譯 `Image`／`File`／`Files` 欄位，locale 物件裡另外會有一個去掉 `Id`
尾巴的解析鍵——`heroImageId` 同時會有 `heroImage`，放解析出來的檔案列或 `null`；解析需要對
`file` 的讀取授權，沒有授權時這個鍵是 `null`，原始 id 仍然會送出。名字不是以 `Id` 結尾的欄
位不會有這個解析鍵。

`Hidden` 的可翻譯欄位連名字帶值都不外洩：回應裡會把它從每個 locale 物件裡拿掉；schema 把它
從 `translation.fields` 清單裡拿掉的部分，[第 6 章：欄位型別與編輯介面](06-field-types.md)
已經說過。

### GraphQL

GraphQL 讀翻譯是一個清單，不是一張映射表：有 sidecar 的集合會多一個
`translations: [Translation!]`，共用的 `Translation` 型別是 `{ locale: String!, fields:
Any! }`，`fields` 是通用 JSON 純量，放那個 locale 的欄位映射。

寫入翻譯走的是每個集合自己的型別化輸入，不是通用映射：每個可翻譯欄位對應一個輸入欄位，包成
`{ locale, fields }`，掛在每個 create／update mutation 上；resolver 把這個清單折疊成跟 REST
一樣、以 locale 為鍵的物件，同一個 locale 在清單裡出現兩次時，後面的贏。可翻譯的父層欄位本
身會從 GraphQL 的 create／update 輸入型別裡排除，型別化的翻譯輸入是那裡唯一能寫入的方式。

## 後台的語言分頁與完成度

只有集合真的有可翻譯欄位時，後台才會顯示語言分頁，每個已啟用的語言各一個分頁，就算只啟用
一種語言也一樣；預設語言的分頁會多一個星號標記。

每個分頁標籤上的完成度圓點，只在已啟用的語言超過一種、而且集合有可翻譯欄位時才會出現。

一個 locale 的圓點，只要它任何一個可翻譯欄位有值就會亮起。所謂有值，指去除空白後不是空字
串、不是空陣列，或任何其他不是 `null`／`undefined` 的值；數字（含 `0`）與布林（含 `false`）
都算有內容。

這純粹是後台根據已載入的表單資料算出來的訊號，不是驗證結果，跟伺服器端逐 locale 的
`Required` 規則沒有關係。

編輯畫面載入項目時帶齊所有語言，每個分頁都顯示已存的內容。儲存時只送有內容的 locale，伺服器
再逐欄位合併。

表單的建立與更新規則不一樣：

- 建立時：預設語言就算整個空白也會送出，非預設語言整個空白就跳過。
- 更新時：整個空白的 locale 都跳過，包含預設語言。

表單逐 locale 驗證。預設語言一定會檢查；其他語言只在有內容時才檢查，所以沒碰過的分頁不會擋住
儲存。

每個錯誤顯示在自己的分頁上，有錯誤的分頁標籤上會有標記，儲存失敗時會跳到第一個有錯誤的分
頁。伺服器的翻譯錯誤帶有 `locale`，表單會把它對應到那個分頁。欄位上的必填星號只出現在預設
語言的分頁。
