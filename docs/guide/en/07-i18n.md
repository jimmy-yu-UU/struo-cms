# 7. Multilingual Content

How a field stores a separate value for each language, and how the API and the admin SPA show those
translations, are what this chapter covers.

## Two kinds of locale: content and interface

Multilingual content has two independent concepts:

- The content locale decides which copy of a translatable field a read or write acts on. It comes
  from the `languages` table, from `?locale=` on read, and from the locale keys inside the
  `translations` object on write.
- The interface locale only decides which language the admin UI's own text is shown in. It's
  handled entirely on the frontend, switched through the `UiLanguageSwitcher` component, and never
  reaches the API or touches the `languages` table.

## The `languages` table and `GET /api/languages`

A content locale is a row in the framework's own `Language` entity, which is itself a
`[CmsCollection]` in the `System` group — so besides its own read endpoint, it's also editable
through the ordinary items API at `/api/items/language`. Each row carries `code`, `name`,
`isDefault`, `enabled`, and `sort`. A fresh install seeds two enabled languages by default: `en`
(`isDefault`) and `zh-TW`.

`GET /api/languages` is open to any signed-in caller, not only an admin. It returns only the
enabled languages, projected to `code`, `name`, and `isDefault`. The default locale resolves in
order:

1. The enabled row with `isDefault`.
2. Otherwise, the enabled row with the lowest `sort`.
3. Otherwise, the literal `"en"`.

Locale codes compare case-insensitively. The set of enabled languages is computed once per request
scope, and every locale check on read and write goes through that same provider — so disabling a
language row takes effect on the very next request, with no restart needed.

## Making a field translatable

A field becomes per-locale by declaring it on the sidecar type named by `[CmsTranslations]`, not by
setting `Translatable = true` on the parent field. Every field declared on a sidecar is translatable
regardless of what its own `Translatable` setting says.

Writing `Translatable = true` on a parent `[CmsField]` instead has no effect: there is no sidecar
behind it, so the required check skips the field, and so do the `MaxLength` check and every
per-interface validator, while the write body still binds it, and reads never resolve it per
locale. The field's metadata looks translatable, but it never actually varies by language.

The scanner folds every sidecar field into the parent collection's own field list, so a
translatable field can be filtered, searched, and sorted like any other field — it just resolves
against the sidecar table at the effective query locale.

The effective query locale is `?locale=` when supplied, and the default locale otherwise, so
filtering on a translatable field works even with no `?locale=` at all. An item with no translation
row for a locale is excluded by a filter on it, and sorts as `NULL`.

Six interfaces can't be translatable: `MultiSelect`, `CheckboxGroup`, `Tags`, `KeyValue`, `Files`,
and `Repeater`. Setting `Translatable = true` on any of them is a startup `MetadataException`:
`Field '{name}' uses interface '{Interface}', which cannot be translatable.` `Json` is deliberately
left out of that set, so a per-locale multi-select or repeater isn't possible, but per-locale raw
JSON is.

## The translation sidecar

The per-locale sidecar is a plain SqlSugar entity — it is not itself a
`[CmsCollection]` — linked from the parent by an ignored list property carrying
`[CmsTranslations(typeof(TSidecar))]`. The sample's `Article` declares it like this:

```csharp
[CmsTranslations(typeof(ArticleTranslation))]
[SugarColumn(IsIgnore = true)]
public List<ArticleTranslation> Translations { get; set; } = [];
```

A sidecar type must declare four things, or the scan fails at startup with its own
`MetadataException` for each:

- A property named `Id`.
- A foreign key named by the `{ParentTypeName}Id` convention.
- A `string` property named exactly `Locale`.
- At least one `[CmsField]`.

`ArticleTranslation` shows the complete shape:

```csharp
using SqlSugar;
using Struo.Domain.Metadata.Attributes;
using Struo.Domain.Metadata.Enums;

namespace Struo.Sample.Blog;

[SugarTable("article_translations")]
public sealed class ArticleTranslation : Struo.Domain.Seo.SeoTranslation
{
    [SugarColumn(IsPrimaryKey = true, IsIdentity = true)] public long Id { get; set; }
    public Guid ArticleId { get; set; }
    public string Locale { get; set; } = "";
    [CmsField(Label = "Title", Interface = FieldInterface.Text, Required = true, Searchable = true, Sortable = true, Sort = 1, Group = "Content")]
    public string Title { get; set; } = "";
    [SugarColumn(IsNullable = true)]
    [CmsField(Label = "Body", Interface = FieldInterface.RichText, Sort = 2, Group = "Content")]
    public string? Body { get; set; }
    [SugarColumn(IsNullable = true)]
    [CmsField(Label = "Internal Slug", Interface = FieldInterface.Text, Hidden = true, Sort = 3, Group = "Content")]
    public string? InternalSlug { get; set; }
}
```

The `(fk, locale)` unique index isn't declared by hand — CodeFirst adds it automatically when the
table is created, so a parent can have at most one translation row per locale.

A sidecar table that already exists without the index doesn't gain it retroactively; that takes an
ordinary migration.

The one exception is a Development environment with `Database:AutoSyncSchema` enabled: its full
sync tries to add the index, and if the table already holds duplicate `(fk, locale)` rows, startup
fails outright — surfacing the bad data instead of hiding it.

Development startup also re-checks that every sidecar table actually has this unique index, and
throws an error naming the table when one is missing. The check runs only on PostgreSQL and SQLite;
the other three backends aren't checked.

## Per-locale SEO

`SeoTranslation` is an abstract base class a sidecar can inherit for three ready-made
`Group = "SEO"` fields: `SeoTitle` (`Text`), `SeoMetaDescription` (`Textarea`), and `SeoOgImageId`
(`Image`). SEO exists only per locale — there's no shared parent-side fallback.

## Default locale and write rules

Create always requires a translation for the default locale; missing it rolls back the whole
write:

```text
$ POST /api/items/article
body:
{"status":"draft"}
{"success":false,"error":{"code":"BAD_USER_INPUT","message":"A translation for the default locale 'en' is required."}}
HTTP_STATUS:400
```

An absent `translations`, a non-object value, an empty object, or one that never mentions the
default locale all fail with the same 400.

Update relaxes the rule: an absent or non-object `translations` counts as a no-op partial update,
so a caller can update only the parent fields, or only one non-default locale, without resupplying
every language. A locale key that exists but isn't enabled is rejected the same way on read and
write: `Unknown or disabled locale '{locale}'.`

On read, a locale code is charset-validated before the enabled check even runs — it must match
`[A-Za-z0-9_-]{1,35}` — which keeps injection characters out of `?locale=`; the same validation
applies to the locale keys inside a write's `translations` object.

A translatable field's `MaxLength` is checked per locale, and the error names which one:
`Field '{name}' exceeds maximum length {n} for locale '{locale}'.`

A locale object itself carries three more validation rules:

- A key that isn't one of the sidecar's own translatable fields is rejected: `Field '{name}' is not
  a translatable field of '{collection}'.`
- A translatable field marked `Required` on the sidecar must be non-empty for every locale
  supplied, not only the default: `Required translation field '{name}' is missing for locale
  '{locale}'.`
- A locale's own value must itself be an object: `Translation for locale '{locale}' must be an
  object.`

Writing a locale replaces the whole row: the sync deletes that locale's existing row first, then
inserts a new one, so a field the write omits falls back to the sidecar property's own initializer
— a non-nullable `string` such as `ArticleTranslation.Title` becomes `""`, a `string?` becomes
`null`, not uniformly cleared to `null`.

A locale the write doesn't mention is untouched; sending only `{"en": {"title": "x"}}` clears
`en`'s other translatable fields to their own property defaults.

Two locale keys in the same write that differ only in case merge, with the later one winning; the
locale mapping itself is case-insensitive.

## Translations in REST and GraphQL responses

### REST

A collection with a sidecar always carries a `translations` object on every projected row, attached
after its own fields are projected — even with `fields=`, `translations` is never filtered out.
Without `?locale=`, it holds every locale that has a translation row, keyed by locale code:

```text
$ GET /api/items/article/01a08c68-57d6-7f25-80e7-c42a2a1702a4
{"success":true,"data":{"id":"01a08c68-57d6-7f25-80e7-c42a2a1702a4","version":0,"status":"draft","publishedAt":null,"heroImageId":null,"regions":[],"audiences":[],"keywords":[],"attributes":null,"meta":{},"gallery":[],"faqs":[],"createdAt":"2026-09-10T17:40:43.607052","createdBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","updatedAt":"2026-09-10T17:40:43.607133","updatedBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","translations":{"en":{"title":"Getting started with StruoCMS","body":"<p>Run the API and the admin SPA.</p>","seoTitle":null,"seoMetaDescription":null,"seoOgImageId":null,"seoOgImage":null},"zh-TW":{"title":"開始使用 StruoCMS","body":"<p>先把 API 與後台跑起來。</p>","seoTitle":null,"seoMetaDescription":null,"seoOgImageId":null,"seoOgImage":null}}}}
HTTP_STATUS:200
```

One entry per locale, keyed by the locale code.

With `?locale=`, the object narrows to that one locale; when the parent has no translation row in
it, the value is an empty object `{}` — not a missing key, and not `null`:

```text
$ GET /api/items/article/01a08c68-58a8-78cd-82cc-c80d609530c6?locale=zh-TW
{"success":true,"data":{"id":"01a08c68-58a8-78cd-82cc-c80d609530c6","version":0,"status":"draft","publishedAt":null,"heroImageId":null,"regions":[],"audiences":[],"keywords":[],"attributes":null,"meta":{},"gallery":[],"faqs":[],"createdAt":"2026-09-10T17:40:43.817217","createdBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","updatedAt":"2026-09-10T17:40:43.817477","updatedBy":"019f1794-82d6-70b2-8e07-e7ecdf37b858","translations":{}}}
HTTP_STATUS:200
```

This is a different article with no zh-TW row, so `translations` comes back as an empty object
rather than falling back to the default locale.

`?locale=` is a strict filter with no fallback at all: a missing translation means the locale
has no key at all, never the default locale's value and never a `null` placeholder — the frontend
has to handle the missing key itself.

A translatable field's value never appears on the parent row: the projector produces no top-level
key for it at all, so the only place to read it is under `translations`.

A translatable `Image`/`File`/`Files` field whose name ends in `Id` also gets a resolved sibling key
in the locale object with the `Id` suffix dropped — `heroImageId` comes with a `heroImage` holding
the resolved file row, or `null`. Resolving it needs read access to `file`; without that grant the
key is `null` and the raw id still comes through. A field whose name doesn't end in `Id` gets no
resolved key.

A `Hidden` translatable field leaks neither its name nor its value: it's dropped from every locale
object in the response, and the schema side drops it from `translation.fields` too, as
[Chapter 6: Field Types and Editors](06-field-types.md) already covers.

### GraphQL

GraphQL reads translations as a list, not a map: a collection with a sidecar gains
`translations: [Translation!]`, where the shared `Translation` type is
`{ locale: String!, fields: Any! }` and `fields` is the generic JSON scalar holding that locale's
field map.

Writing translations goes through each collection's own typed input instead of a generic map: one
input field per translatable field, wrapped as `{ locale, fields }` and carried on every
create/update mutation. The resolver folds that list into the same locale-keyed object REST uses,
with the later duplicate locale winning. A translatable parent field is itself excluded from the
GraphQL create/update input types — the typed translations input is the only way to write it.

## Locale tabs and completeness in the admin SPA

The admin SPA shows locale tabs only when a collection actually has translatable fields, one tab per
enabled language, even when only one language is enabled; the default locale's tab carries an extra
asterisk.

The completeness dot on each tab label appears only when more than one language is enabled and the
collection has translatable fields.

A locale's dot fills as soon as any one of its translatable fields holds a value — a trimmed
non-empty string, a non-empty array, or any other value that isn't `null`/`undefined`. Numbers
(including `0`) and booleans (including `false`) count as content.

This is purely a frontend signal computed from the form data already loaded — not a validation
result, and unrelated to the server's per-locale `Required` rule.

The form fetches the item once, at the default locale, so every non-default tab starts out empty
regardless of what's actually stored; saving sends only the locales that hold content, which is
exactly why a tab nobody opened never gets wiped.

The form's create and update rules differ:

- Create: the default locale is sent even when entirely blank; a blank non-default locale is
  skipped.
- Update: any entirely blank locale is skipped, including the default.

A translatable field's required marker and its client-side error message render only on the default
locale's tab; a missing required translation on a non-default locale isn't flagged by the form
itself — it waits for the server to reject it.
