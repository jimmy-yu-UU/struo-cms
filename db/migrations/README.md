# Schema migrations

Reviewed, forward-only SQL scripts that evolve the **PostgreSQL** production schema. `InitTables`
(SqlSugar CodeFirst) only *creates* missing tables in Development — it cannot alter/drop columns — so
every post-deploy schema change lives here as a checked-in, versioned script. See
[chapter 15](../../docs/guide/en/15-deployment-operations-testing.md) for the full operational picture
(schema management, startup behavior, backups, tests, CI).

## The baseline: `001-core-baseline.sql`

This folder holds a single script, **`001-core-baseline.sql`**, the complete **core-framework**
schema — the 10 `FrameworkEntityTypes` tables (`languages`, `files`, `file_translations`,
`media_folders`, `users`, `roles`, `permissions`, `user_roles`, `revisions`, `site_settings`) plus
their primary keys, unique constraints, and indexes. It was machine-generated by running
`InitTables(FrameworkEntityTypes.All)` against a scratch PostgreSQL database and dumping the result
with `pg_dump --schema-only`, then hand-hardened to be idempotent (`CREATE TABLE IF NOT EXISTS`,
`CREATE [UNIQUE] INDEX IF NOT EXISTS`, PKs inlined) and stripped of `pg_dump` session preamble. Because
it is generated straight from the entity classes, it cannot drift from what `InitTables` produces for
the same entity set.

**Scope is core only.** StruoCMS is a reusable CMS *template*: the sample Blog schema (`articles`,
`tags`, `categories`, and related tables) is a demo built by `InitTables` in dev and is deliberately
**not** in this baseline. Business/sample schema is a downstream concern — see "Downstream forks"
below.

## How the environments use it

- **Dev:** `InitTables` builds both core and sample tables straight from the entity classes on every
  startup. `Database:MigrationsPath` stays **empty** in dev, so the runner never runs and the baseline
  file is not applied here at all. It doesn't need to be — if it were ever pointed at a dev database it
  would just no-op (`IF NOT EXISTS` against tables `InitTables` already created).
- **Production:** there is no `InitTables` in Production. Set `Database:MigrationsPath` to this
  directory and let `MigrationRunner` apply `001-core-baseline.sql` to an **empty** database at
  startup. That single file is enough to bootstrap the entire core schema — no dependency on the
  Development-only CodeFirst path.
- **Test:** the test suite runs on SQLite. `MigrationRunner` is PostgreSQL-only and is a **hard no-op**
  on any other backend — it neither reads nor creates the tracking table and runs no SQL.

## Adding the next script

```
NNN-short-kebab-description.sql
```

- **`NNN`** — zero-padded, **contiguous, single series**. The numeric prefix is the apply order
  (ordinal filename sort), so it must be monotonic and gap-free. The next migration is simply the
  highest existing number **+ 1** — as of this file, the next script after the `001` baseline is
  `002-…`.
- **`short-kebab-description`** — one logical change per file.
- Each file starts with a header comment: date, author, and a one-line intent (see
  `001-core-baseline.sql` for the pattern).
- Scripts must be **idempotent** (`IF NOT EXISTS`, guarded `ALTER`, `DO $$ … $$` existence checks) so a
  re-run is safe. **Forward-only** — no automatic `down`; write a compensating forward script if a
  rollback is needed.
- **Timestamp convention:** any new column or table that stores an instant uses `timestamptz`
  (timestamp *with* time zone), never bare `timestamp`, storing UTC and letting the client localize.
  The precedent is the runner's own tracking table, described below. The baseline itself is not
  uniform: most `AuditableEntity` `createdat`/`updatedat` columns are bare `timestamp`, but
  `media_folders.createdat`/`media_folders.updatedat` and `site_settings.updatedat` (`site_settings` has
  no `createdat` column at all) are already `timestamptz` — check `001-core-baseline.sql` for the table
  you are altering rather than assuming either type from this list. None of the baseline's existing
  bare-`timestamp` columns are retro-migrated to close that gap — retro-converting already-stored values
  re-anchors them against the session time zone, a silent data shift for anything not already written in
  UTC. The convention binds new schema only.

## The runner: tracking table and transaction behavior

A lightweight runner (`MigrationRunner`, in `Struo.Infrastructure/Persistence`) applies pending scripts
at application startup:

- **PostgreSQL only.** On any other backend (e.g. the SQLite used by the test suite) it is a hard
  no-op — it neither reads nor creates the tracking table and runs no SQL.
- Enabled by configuration: set `Database:MigrationsPath` to this directory (an **absolute** path in
  Production — chapter 15 covers why a relative path is dangerous there). Empty/absent (the default)
  disables it. It runs in **all** environments when configured, positioned after `InitTables` and
  before `DataSeeder`'s initial-data seeding — that seeding itself runs in every environment, not only
  dev (`src/Struo.Api/Program.cs`), so on the Production path this file documents, `MigrationRunner`
  creates `users`/`roles` and then `DataSeeder` seeds the bootstrap admin and RBAC rows against them.
- Tracks applied filenames in a `schema_migrations (filename text PRIMARY KEY, appliedat timestamptz)`
  table it creates on first run. Tracking is by **filename only** — no checksum or content hash — so an
  already-recorded file is never re-run even if its on-disk content later changes. Never edit a
  filename that may already be recorded as applied anywhere; ship a new file instead.
- Each file runs inside its own transaction together with its tracking-row insert; the first failure is
  rolled back and aborts the run (later files are not attempted).

## Fresh environment (bootstrap)

1. Create the empty PostgreSQL database and set `Database:ConnectionString`.
2. Choose how the baseline schema is created:
   - **Dev / disposable:** run the app once in `Development` with `Database:MigrationsPath` empty (the
     default) — `InitTables` creates core + sample tables from the entity classes. The runner does not
     run.
   - **Production:** do **not** rely on `InitTables`. Set `Database:MigrationsPath` to this directory
     (absolute path) and let `MigrationRunner` apply `001-core-baseline.sql` to the empty database at
     startup — that is the entire core schema, no manual step required beyond configuration.
3. On every subsequent deploy, add the new `NNN-…` script(s) for whatever schema change is needed; the
   runner applies only the ones not yet recorded in `schema_migrations`.

## Downstream forks

A fork that adds its own business collections should delete the sample Blog project entirely and then
add its own `NNN-…` migration scripts for its own tables, starting at `002-…`.
`001-core-baseline.sql` remains untouched as the shared core starting point every fork bootstraps from.

## Manual apply (no runner)

Apply files in ascending `NNN` order with a reviewed SQL client, back up first, and record applied
files yourself (the runner uses `schema_migrations`; by hand, keep an ops log or insert rows).
