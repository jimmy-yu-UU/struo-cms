# Schema migrations

Reviewed, forward-only SQL scripts that evolve the **PostgreSQL** production schema. `InitTables`
(SqlSugar CodeFirst) only *creates* missing tables in Development — it cannot alter/drop columns — so
every post-deploy schema change lives here as a checked-in, versioned script.

See [`docs/migration-strategy.md`](../../docs/migration-strategy.md) for the "why" (audit finding D3).

## The baseline: `001-core-baseline.sql`

This folder currently holds a single script, **`001-core-baseline.sql`**, the complete **core-framework**
schema — the 9 `FrameworkEntityTypes` tables (`languages`, `files`, `file_translations`, `users`, `roles`,
`permissions`, `user_roles`, `revisions`, `site_settings`) plus their primary keys, unique constraints, and
indexes. It was machine-generated by running `InitTables(FrameworkEntityTypes.All)` against a scratch
PostgreSQL database and dumping the result with `pg_dump --schema-only`, then hand-hardened to be
idempotent (`CREATE TABLE IF NOT EXISTS`, `CREATE [UNIQUE] INDEX IF NOT EXISTS`, PKs inlined) and stripped
of `pg_dump` session preamble. Because it is generated straight from the entity classes, it cannot drift
from what `InitTables` produces for the same entity set.

**Scope is core only.** StruoCMS is a reusable CMS *template* (CLAUDE.md §0): the sample Blog schema
(`articles`, `tags`, `categories`, `article_tags`, `article_translations`, …) is a demo built by
`InitTables` in dev and is deliberately **not** in this baseline. Business/sample schema is a downstream
concern — see "Downstream forks" below.

## How the environments use it

- **Dev:** `InitTables` builds both core and sample tables straight from the entity classes on every
  startup, exactly like before. `Database:MigrationsPath` stays **empty** in dev (decision BL-5), so the
  runner never runs and the baseline file is not applied here at all. It doesn't need to be — if it were
  ever pointed at a dev DB it would just no-op (`IF NOT EXISTS` against tables `InitTables` already
  created).
- **Production:** there is no `InitTables` in Production. Set `Database:MigrationsPath` to this directory
  and let `MigrationRunner` apply `001-core-baseline.sql` to an **empty** database at startup. That single
  file is enough to bootstrap the entire core schema — no dependency on the Development-only CodeFirst
  path. This is the self-bootstrap path for a fresh production deploy.
- **Test:** the test suite runs on SQLite. `MigrationRunner` is PostgreSQL-only and is a **hard no-op** on
  any other backend — it neither reads nor creates the tracking table and runs no SQL.

## Downstream forks

A fork that adds its own business collections should delete the sample Blog project entirely and then add
its own `NNN-…` migration scripts for its own tables, starting at `002-…`. `001-core-baseline.sql` remains
untouched as the shared core starting point every fork bootstraps from.

## Numbering convention

```
NNN-short-kebab-description.sql
```

- **`NNN`** — zero-padded, **contiguous, single series**. The numeric prefix is the apply order (ordinal
  filename sort), so it must be monotonic and gap-free.
- **`short-kebab-description`** — one logical change per file.
- The **next migration** is simply the highest existing number **+ 1**. As of this file the baseline is
  `001`, so the next script is `002-…`.

Each file starts with a header comment: date, author, ticket/PR, and a one-line intent (see
`001-core-baseline.sql` for the pattern). Scripts must be **idempotent** (`IF NOT EXISTS`, guarded `ALTER`,
`DO $$ … $$` existence checks) so a re-run is safe. Forward-only — no automatic `down`; write a
compensating forward script if a rollback is needed.

## Timestamp convention (DB-7)

New columns and new tables that store an instant use **`timestamptz`** (timestamp *with* time zone),
never bare `timestamp`. Store UTC; let the client localise. The precedent is the runner's own tracking
table — `schema_migrations (filename text PRIMARY KEY, appliedat timestamptz)`, created by
`MigrationRunner` (whose code comment states the same convention). Any future `NNN-…` script that adds a
temporal column must follow it.

Existing `timestamp` columns in the baseline (all `AuditableEntity` `createdat`/`updatedat` columns except
`site_settings.updatedat`, which is `timestamptz`) are **not** retro-migrated: a retro-conversion
re-anchors already-stored values against the session time zone (a silent data shift for anything not
written in UTC), so the cost/risk outweighs the benefit for columns that already exist. The convention
binds new schema only; leave the baseline's existing columns as-is unless a specific defect requires a
deliberate, reviewed conversion script.

## Applying — the runner

A lightweight runner (`MigrationRunner`, in `Struo.Infrastructure/Persistence`) applies pending scripts
at application startup:

- **PostgreSQL only.** On any other backend (e.g. the SQLite used by the test suite) it is a hard
  no-op — it neither reads nor creates the tracking table and runs no SQL.
- Enabled by configuration: set `Database:MigrationsPath` to this directory. Empty/absent (the default)
  disables it. It runs in **all** environments when configured (that is the point — reviewed scripts get
  applied to production), positioned after `InitTables` and before the dev seeders.
- Tracks applied filenames in a `schema_migrations (filename text PRIMARY KEY, appliedat timestamptz)`
  table it creates on first run. Already-recorded filenames are skipped, so it is safe to re-run.
- Each file runs inside its own transaction together with its tracking-row insert; the first failure is
  rolled back and aborts the run (later files are not attempted).

Example (`appsettings.json` / environment override):

```json
"Database": {
  "MigrationsPath": "db/migrations"
}
```

## Fresh environment (bootstrap)

1. Create the empty PostgreSQL database and set `Database:ConnectionString`.
2. Choose how the baseline schema is created:
   - **Dev / disposable:** run the app once in `Development` with `Database:MigrationsPath` empty (the
     default) — `InitTables` creates core + sample tables from the entity classes. The runner does not run.
   - **Production:** do **not** rely on `InitTables`. Set `Database:MigrationsPath` to this directory and
     let `MigrationRunner` apply `001-core-baseline.sql` to the empty database at startup — that is the
     entire core schema, no manual step required beyond configuration.
3. On every subsequent deploy, add the new `NNN-…` script(s) for whatever schema change is needed; the
   runner applies only the ones not yet recorded in `schema_migrations`.

## Manual apply (no runner)

Apply files in ascending `NNN` order with a reviewed SQL client, back up first, and record applied
files (the runner uses `schema_migrations`; by hand, keep an ops log or insert rows yourself).
